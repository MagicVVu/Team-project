# MagicVVu 数据库设计 v0.3（家庭共享清单版，修订 2026-10-14）

## 一、正式确定的产品规则

1. **一个家庭共用一份购物清单**，不是每位用户拥有自己的清单；数据库对 `shopping_lists.household_id` 加唯一约束，因此同一家庭**最多**一份清单。创建家庭时，同一事务应自动建立该家庭清单，才能在业务上满足「每家恰好一份」。
2. 每个清单项记录 `added_by_user_id`（添加者），勾选「已购买」时记录 `purchased_by_user_id`（购买者）与 `checked_at`（购买时间）。历史数据允许添加者为空，UI 展示「未知/历史记录」。
3. **勾选已购买时自动入库**：在一个数据库事务中更新购物项状态、创建一个库存批次，事务失败则全部回滚。
4. **防重复入库**：新库存的 `source_shopping_list_item_id` 唯一，购买操作先锁定清单项（PostgreSQL `SELECT ... FOR UPDATE`），同一项被重复点击或并发购买不会重复创建库存。
5. 已购买项目**保留在共享清单内作为历史**，UI 默认显示未购买清单，可折叠展示已购买；不允许通过「取消勾选」简单重新入库。如需再次购买同种商品，应创建新清单项。
6. 入库时复制商品名称、购买数量和单位，记录购买日期、操作用户和来源清单项。**不同日期、保质期的物品不盲目合并**，即使名称相同也创建独立库存批次；储存位置和有效期允许在入库时补充，未提供则保持 NULL。
7. 家庭成员能否购买要经过权限检查；用户身份应来自后续 JWT 会话，而不是信任客户端上传的用户 ID。AI Agent 同样只能调用经过认证的后端业务接口。
8. 当前升级只提供**表结构 + 内部购买入库服务 + 回滚式测试**，暂不开放业务公网 API。前端勾选触发真实入库，还需下一阶段开发认证和购买路由。

## 二、六张业务表及关联

| 表 | 主要内容 | 关联 / 约束 |
|---|---|---|
| `users` | 登录信息（安全密码哈希）、昵称 | `email` 唯一且小写 |
| `households` | 家庭名称、创建者 | 创建者指向 `users` |
| `household_members` | 家庭成员、角色（owner/admin/member） | (`household_id`, `user_id`) 组合主键 |
| `inventory_items` | 家庭库存批次、数量、单位、购买日期、到期时间、位置 | 属于家庭；`source_shopping_list_item_id` 可空、**唯一**，指向来源清单项 |
| `shopping_lists` | 家庭唯一共享清单 | `household_id` 唯一、指向家庭 |
| `shopping_list_items` | 商品名称、数量、单位、是否购买、添加者、购买者、购买时间 | 属于清单；关联 `users` |

关系：`users` N—N `households`（通过 `household_members`）；`households` 1—0..1 `shopping_lists`（数据库）；`shopping_lists` 1—N `shopping_list_items`；`households` 1—N `inventory_items`；`shopping_list_items` 1—0..1 `inventory_items`（本操作产生的库存批次）。

### 购物清单主要字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `shopping_lists.household_id` | UUID | 家庭 ID；唯一，阻止一家庭多清单 |
| `shopping_list_items.added_by_user_id` | UUID, nullable | 添加者；历史数据为 NULL；新建业务接口必须写入真实成员 ID |
| `shopping_list_items.is_checked` | BOOLEAN | 已购买/已入库标记；沿用旧字段兼容迁移 |
| `shopping_list_items.checked_at` | TIMESTAMPTZ | 购买时间；沿用旧字段 |
| `shopping_list_items.purchased_by_user_id` | UUID, nullable | 标记购买的家庭成员；历史数据可为空 |
| `inventory_items.source_shopping_list_item_id` | UUID, nullable, UNIQUE | 与来源清单项一一关联，避免重复入库；手动添加库存时为空 |

其余字段仍沿用原 v0.3 设计：库存 `quantity NUMERIC(12,3) >= 0`；购物项 `quantity NUMERIC(12,3) > 0`；购买数量和单位直接复制。图片仅保存对象存储 key。

### 为什么不把清单勾选直接改成 SQL UPDATE？

单独执行 `UPDATE shopping_list_items SET is_checked = true` **不会**自动入库。必须由 `app.services.shopping.purchase_and_stock` 统一执行关联状态修改和库存创建，并在调用者的事务中一次提交。未来的认证 API 将调用这个服务。

### 是否会产生重复库存？

一个清单项恰好对应一次购买动作。`FOR UPDATE` 锁 + 唯一来源约束保证重复请求不创建第二条库存。假设用户连续点击两次「购买牛奶 2 瓶」：第一次添加 **2 瓶**库存，第二次得到第一次生成的库存 ID，而不是累计到 4 瓶。若之前存在旧式「已勾选但没有来源库存链接」的行，服务返回需人工对账错误，**不会猜测并再次入库**。

## 三、迁移安全性

本次**保留原始** `20261014_0001_core_tables.py`，并新增迁移 `20261014_0002_shared_shopping.py`：

- v0.2（无业务表）升级：依次执行 0001 → 0002。
- 旧 v0.3（已执行 0001）升级：仅执行 0002。
- 如果已有某个家庭多份清单，0002 **主动中止迁移**，需要先备份并合并清单及条目；不自动删除任何业务数据。
- 新增用户归属字段对已有记录允许 NULL，避免旧数据升级失败。新 API 必须强制鉴权且记录真实添加者/购买者。
- 不自动补录旧清单中已购买项目的库存：必须明确核实避免重复。
- 不建议直接运行 downgrade：旧数据的来源和购买者信息可能丢失；如遇问题优先停止并基于备份恢复。
