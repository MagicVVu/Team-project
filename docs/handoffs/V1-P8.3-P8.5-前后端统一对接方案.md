# V1-P8.3～P8.5 前后端统一对接方案

更新：2026-10-28，Asia/Shanghai。这里的“三版本”指 **P8.3、P8.4、P8.5**。本文合并三阶段中重复的接入要求，作为本次统一实施入口。历史阶段文档保留开发、评测及发布证据；同一接入事项按本文的最终口径执行，不逐版重复开发。

**最终路线：P8.3 规划结果与重验契约＋P8.5 会话三阶段＋P8.4 既有任务保存、草稿修订、确认与恢复机制。** 前端一次接公开新版会话，后端一次完成 P8.5 适配，AI 一次准备包含上述能力的候选运行版本。

本文件是实施方案，不表示适配已完成。此次只核对本地源码、JSON 契约和已保存发布记录，未重新登录服务器；不据历史记录断言当前线上配置。本轮仅整理文档和目标契约，不修改前后端业务源码、不部署。

## 5. 统一主流程

### 5.1 前端初始化与发消息

1. 登录/切家庭后读取 `GET /api/v1/agent/execution-capabilities`，区分会话协议和动作执行能力。
2. 打开助手先 `GET /api/v1/agent/conversation?household_id=...&limit=20`。按 next_cursor 请求更早历史，避免分页重复；历史只展示原状态，当前任务用最新 active_task。
3. 只有没有会话且 `requires_reset=true` 时初始化 reset；每次打开窗口都reset会丢掉当前会话边界，不能这样做。
4. 使用 `POST /api/v1/agent/conversation-turns`。旧URL不能仅改名：要按下列请求结构保存所有选择器。

```json
{
  "household_id": "22222222-2222-4222-8222-222222222222",
  "request_id": "chat-20261028-001",
  "conversation_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "conversation_revision": 7,
  "text": "接着之前的牛奶，它现在还剩多少？"
}
```

以上仅示意标识。要继续指定任务时，额外成对提交 task_id/revision；不发送 batch_id、context、archive、history、basis、执行状态或用户/家庭可信事实。新文本生成新request_id，超时恢复保留原ID和原完整请求。

### 5.2 后端处理一个新回合

1. 核实成员资格、当前会话、请求摘要、会话修订、任务选择器及并发占用。按已有方式预留 ConversationTurn，不能另建一条AI执行通道。
2. 构建 context（当前任务、原候选顺序、最近明确对象、最近十轮、最新任务/回执证据）和 archive（真实已完成相关历史的候选集）。保存本请求固定的用户原文和协议。
3. 调用 `/agent/dialogue/p85/understand`，保存完整理解结果及 context_revision，再进入下一阶段。不能调用旧提取器二次理解。
4. 在理解结束后重新核实权限、会话修订和任务/回执，构建新鲜context及与其同修订的archive。传原 plan、原 plan_context_revision 到 `/agent/dialogue/p85/resolve`；修订冲突必须刷新，不能偷偷改 plan_context_revision 来通过。
5. 先保存已验证的 resolved，再决定表达。只有本轮理解用过模型、不是恢复/结构化澄清、`expression_required=true` 且预算充足时，才调用 respond；否则采用 resolve.reply。
6. 普通聊天可能已经自然回答，`expression_required=false` 时无需第二次润色。表达失败保留事实、草稿和备用回复，不自动重试模型。
7. kind=task 的领域结果通过原网关的 result_provider 保存；kind=clarify 调原结构化续接；kind=edit 用现有业务字段验证和任务/草稿修订保存。保留已有原子提交和锁，不在AI回调写库存。
8. 校验并保存 memory_delta、最终公开回复、来源和调用计数，完成会话修订；公开返回按目标Schema投影，不直接将内部DTO原样透出。

### 5.3 候选、补字段与改口

聊天内打字和选批次按钮优先走同一 conversation-turns 流程。按钮可提交用户看得见的“选择第二批”文字，并带对应 task_id/revision；顺序依据该修订的真实候选，不能按旧列表或手机猜的batch ID。清晰序号由AI确定性解析为结构化答案，后端继续调用原澄清保存流程。

现有独立任务表单仍可用 `POST /api/v1/agent/clarifications/{task_id}` 的 `revision/answers`，它不等于新会话回合。一次提交只能选择一条路径，不能先调澄清又发同一条聊天。直接表单处理后重新GET任务/会话同步版本，不假设它自动追加聊天历史；需要完整聊天记录的窗口使用上述统一回合。

自然语言“还是两盒”产生同任务kind=edit，保留task_id/draft_id，增加相应修订且不延长TTL。手工表单编辑按正式预览/确认的edits字段处理，不要求模型重读表单。尚未提交的本机编辑须按用户/家庭/draft_id/草稿修订隔离保存，并在恢复后重新校验；不能称其已经保存到云端。

### 5.4 正式确认与执行恢复

1. 确认前取得最新 `GET /api/v1/drafts/{draft_id}/execution`。task revision、draft revision与库存expected_version是不同值，不得混用。
2. 本地当前 `execution-preview` 的响应类型专用于OPEN/DISCARD。不要对所有六类动作一律调用该端点；其他动作沿用既有草稿/执行读取和commit校验。
3. 用户明确确认后调用 `POST /api/v1/drafts/{draft_id}/commit`，提交 operation_id、draft_revision、task_revision及允许的edits；不从回复文字拼接新的command。
4. operation_id在本次确认第一次发送前固定保存。响应丢失先GET原operation；无可核实结果时保持“结果待核实”，只能按原草稿、原版本、原operation_id及原请求恢复，不能换ID再扣一次。
5. 只有正式committed回执才能显示执行成功。刷新库存或 `/api/v1/operations/{operation_id}/feedback` 失败，不推翻已核实成功，更不能重做commit。

## 6. P8.5后端适配必须特别处理的细节

### 6.1 协议、类型与原请求恢复

后端新增P8.5分支时，不全局替换旧KEY/DTO。P8.4旧请求按保存的 `dialogue_v1` 和旧AI路由恢复；P8.5请求按 `dialogue_v2` 和新路由恢复。`memory_v1` 会话边界元数据保持兼容。P8.5工厂已保留旧AI路由，业务适配仍须选对。

P8.5理解结果新增context_revision/memory；resolve请求必须带plan_context_revision；结果新增memory/memory_delta/expression_required。旧extra=forbid DTO会直接拒绝这些字段；不能靠只改环境变量启用。

plan_context_revision必须取原understand返回的context_revision，不从手机提交的conversation_revision直接猜填。预留回合和完成回合可能处于不同内部修订阶段；archive.revision与本次context.revision严格一致，delta.expected_revision也应针对该受信处理快照校验。

当前任务的完整P8.5 plan需保存，但传入 `current_task_plan` 时只能投影为其共享Plan类型的字段，不能把memory_id等扩展字段塞入旧严格Plan。保留half/all等原任务语义用于选批次后续算，不能简单丢掉整个任务计划。

表达响应response_calls允许0或1。实际尝试过且结果未知的付费调用仍记审计次数；响应正常时采用经校验的实际计数。总次数不超过2，恢复本次recovery_model_calls为0；不能因恢复而清零原调用审计。

### 6.2 真历史、引用和完成时间

先按用户、家庭、当前conversation_id、reset边界及原ConversationTurn.created_at的30天窗口读历史；只取已完成轮次。不要使用单用户登录游标代替全部家庭历史。最多100片段，AI最多选8个；未读完整时设置has_more。历史和当前候选超限必须明示，不能暗删候选或改变顺序。

在现有JSON中保存可信completed_at，不新增列；其值应不早于该轮正式保存、来源引用签发。历史展示仍用原created_at。P8.5要求episode.reference.issued_at不晚于episode.created_at：将核对前的delta时间直接配上之后签发的新引用，会导致下一轮校验失败。用真实完成时间映射 `P85StoredTurn.completed_at`，同时保留原轮次30天筛选；不能为通过校验改写旧引用的issued_at/expires_at。

subjects只摘录原文名称及原文quote。未得到可核实批次引用时保留reference=null，不从历史名称猜ID。读取旧话题不延长15分钟引用；明确重新查询后可按正式业务规则签发新引用，这与读旧记忆续期是两回事。

后端必须将**本请求自己读取并提供给AI的archive中的原引用**纳入允许返回的引用集合，与当前reference/choices一样逐字段核对，再读取来源任务/修订、权限和有效期。不能沿用当前仅允许context.reference/choices的集合，否则历史话题会触发MEMORY_AI_INVALID_REFERENCE；也不能改成无条件接受AI返回的任意引用。

### 6.3 增量保存与公开投影

memory_delta为可选：拒绝/冲突路径可能没有它，不得因缺少delta抹掉原文或报错。存在时核对scope、conversation_id、expected_revision、episode.request_id和source_text_sha256，随原回合结果幂等保存。最终聊天文字使用表达后的公开reply，delta.reply只代表表达前备用文字。

公开顶层继续conversation-memory-1；dialogue.protocol_version记录本轮使用的P8.4/P8.5。公开truncated合并旧截断与memory.truncated；内部archive/selected_ids/summary/delta不直接变成手机可提交的可信上下文。

恢复已完成请求返回原回复，再另给最新active_task/current_conversation_revision；恢复prepared且计划已保存时只resolve并使用确定性回复；processing查询状态；result_unknown不自动再次付费理解。**不得把旧历史草稿的“待确认”解释为最新状态，也不得把历史中的“已完成”当作回执。**

## 7. 前端一次性字段映射与状态规则

| 返回结构 | 前端用途 | 注意 |
|---|---|---|
| reply/original_text/request_id | 聊天气泡与原请求恢复 | 不解析自然文字决定库存写入或执行成功 |
| conversation_id/conversation_revision/current_conversation_revision | 会话标识和并发选择器 | 旧响应恢复后，下一条消息优先用最新修订或重新GET |
| task及task.result | 本轮查询、候选、待补字段、六类草稿及preview | 本轮查其他物品不应覆盖旧活动草稿 |
| active_task.task / active_task.execution | 当前活动任务、草稿修订和最新执行状态 | 优先于历史气泡的状态；不是另一份库存供相加 |
| evidence[kind=verified_calculation].result | 聊天中的统计、预测、风险、规划卡片 | 可能是领域AgentResult或RiskResponse，按类型显示，保留来源和缺口 |
| dialogue.field_sources | 本轮、原任务、计算来源的解释 | 只展示必要信息，不把它变成手机可修改的库存版本 |
| truncated | 使用了部分历史的轻提示 | 不等于任务执行失败，不展示为无限长期记忆 |
| error_code/filled_fields | 可恢复错误、原文及已填信息 | 不清空用户输入，不静默切换本机写入 |

当前聊天三阶段只读计算会把完整计算结果放在evidence中。后端要保留并校验对应结果类型与作用域；前端复用同一个领域结果渲染器处理task.result和verified_calculation.result，避免漏卡片或重复相加。若需投影成新的固定sections字段，须双方另补Schema，不能各自私造字段。本方案复用现有evidence，不新增公开结果通道。

状态至少区分：处理中、待补充、待确认、提交中、已执行、已取消/过期、失败、结果待核实。AI领域的answered只代表查询回答完成。公开聊天响应inventory_written=false只表示**本次聊天未写库存**，不能覆盖active_task内正式业务成功回执；PLAN_ADD可shopping_written=true而inventory_written=false。

所有修订单独保存：会话revision、任务revision、draft_revision、库存expected_version、采购项expected_version、规划basis/version_token。采购版本是摘要值，不按加一推算，避免经Double转换损失精度；按JSON契约和精确整数/字符串类型保存。

切家庭/退出登录清活动绑定；重登再验证权限并恢复相应家庭。“开始新任务”保留本会话，切换业务任务；“开始新会话”用幂等reset切断旧历史/引用，不删除业务任务或取消旧草稿。物品详情“询问这批”的旧reference-messages入口不能擅自给新Message加batch_id；保留明确独立旧入口，或由后端另做受信桥接再合并，不能混用两套绑定。

## 8. P8.3规划与业务页面一起承接

### 8.1 查询、统计和建议

后端向AI提供 `GET /internal/v1/planning/context` 的完整一致快照，保留原data和provenance包络。不要把面向展示的分页流水拼成AI事实，也不要仅转发data丢弃provenance。AI内部使用product:<UUID>选择商品，不代表后端HTTP的item_key接受该字符串；后端当前该查询参数是UUID，AI Reader已有完整快照本地选择逻辑。

前端必须同时区分：显式product_id与batch_id、登记总量与未过登记日期的活动量、未知可用量。不能按名称合并商品，不能把“未过标签日期”写成安全可食用。当前商品级usable_quantity及不满足条件的remaining_days/reference_date/suggested_quantity为null，要展示reason_codes；不要补0或编造耗尽日。

pending_state的none/linked_complete/association_unknown和独立shopping_list_missing分别展示；pending_count可能包含未关联项，pending数组为空不证明待购为零。没有完整消费覆盖时只能称“已登记消费小计”，不能推断实际零消费。丢弃、盘点、更正、归档和商品关联均不计入Consumed统计。

### 8.2 采购来源、商品及资料补录

| 事项 | 复用接口/负责人 | 统一要求 |
|---|---|---|
| 采购来源设置/替换/清空 | PATCH household shopping-list/items/{item_id}；前端 | source省略保留、UUID设置、null清空；operation_id和GET取得的expected_version固定保存 |
| 商品创建及批次关联 | POST products、PUT inventory-items/{item_id}/product；前后端 | 显式用户确认，product_id可null清除；不按同名自动归组；补齐可授权读取后再声称可跨设备选商品 |
| 偏好/记录覆盖/核对资料 | GET/PATCH inventory-items/{item_id}/planning-facts；前端 | 使用expected_inventory_version、expected_facts_version和source；家庭填写不冒充平台审核 |
| 完整账本和库存更正 | GET inventory-events、POST inventory-items/{item_id}/corrections；前端 | 展示真实事件；更正需原因和related_event_id，不将更正当消费或通用撤销 |
| 成员操作摘要 | GET households/{household_id}/operations/{operation_id}/summary；前端 | 使用家庭可见摘要，不冒用另一成员的私有任务读取 |
| 执行后只读反馈 | POST operations/{operation_id}/feedback；前端 | 成功回执优先；PLAN_ADD当前not_applicable，不伪造batch_versions |

以上完整路径及body看现有后端OpenAPI；表内缩写不表示新加路由。商品公开列表/关联读取的缺口由后端负责人补契约，前端不得使用服务Token访问内部规划接口顶替。

### 8.3 依据重验与未开放能力

planning_basis原样保存后端revalidation_basis的精确键和值；计算值放planning_calculation，不向basis加item_key、可编辑量或展示字段。procurement_source保留真实batch_id/expected_version，商品整体无唯一来源不能自动选第一批。

正式确认诊断复用 `POST /api/v1/drafts/{draft_id}/planning-revalidation`；需要刷新建议时，后端携原保存basis/query/diagnostic调用AI内部 `/planning/revalidate`，AI再次读完整快照。stale要求重新读取并核对新建议，blocked继续显示缺口；diagnostic不是以后写入的许可。

自动建议提交事务、审核规则发布/撤销、商品级完整覆盖证明和采购专用反馈等未完成能力继续明确不可用，分别由其负责人建设。本次统一接入不自动放行。手工PLAN_ADD沿用原路径，只加入待购；最低库存规则补货和“本次AI建议”入口不能显示一种依据、执行另一种数量。

## 9. 六类操作只接一条正式执行链

| 动作 | 草稿/可编辑字段口径 | 本地当前后端条件 |
|---|---|---|
| ADD | 名称、数量、单位、必填位置及允许日期 | 已有正式执行路径，创建幂等由业务层负责 |
| CONSUME | 数量、兼容单位；全部模式按最新库存保护 | 正式消费事件，不以普通数量PATCH代替 |
| MOVE | 整批to_location，数量不变 | 已有正式路径；不支持部分拆批 |
| OPEN | opened_at，数量不变 | 已有代码，受MAGICVVU_OPEN_EXECUTION及capabilities约束 |
| DISCARD | 定量quantity/unit或保护的all模式 | 已有代码，受MAGICVVU_DISCARD_EXECUTION及capabilities约束；不以删除替代 |
| PLAN_ADD | 允许的采购quantity/unit，来源受后端保护 | 手工加入待购可用；自动建议仍受规划提交限制 |

标记“已有”只是源码条件，不是本轮真机证明。前端根据真实actions开关、执行预览和校验结果决定按钮；AI有草稿不等于后端已授权执行。动作、目标批次、库存版本和全部模式不能由普通编辑字段改写。已有已执行/取消/过期/未知结果的草稿不得被聊天覆盖或自动重新提交。

### 发布与旧版本保护

本方案不自动同步或替换服务器。将来获授权发布时，AI源码仍按模块放在 `~/workspace/agent`，文档/测试/评测留仓库；使用P8.5完整候选清单，不能漏新目录。启动工厂和健康探针都切P8.5；仅复制源码或只改health文案不算启用。保留原业务后端负责人代码与数据库，不重放0011迁移。

新消息协议开关只有适配、保存和恢复均通过后才设为 `p85-dialogue-1` 并通过capabilities声明；UI不根据业务version=0.9.0或字符串P9猜AI能力。灰度/回滚按新消息能力选择，旧请求始终按其保存协议恢复；不得对结果未知请求自动跨协议重发。

## 11. 联合验收清单与完成标准

| 场景 | 必须看到的结果 |
|---|---|
| 查询两批牛奶→第二批在哪里→移到冷藏室 | 正确批次、最新版本、整批草稿；未确认不写库存 |
| 查询→临时聊天→十轮之外回到初始话题 | 真实历史命中；重新读库存；无记录或过期时如实重新选择 |
| 喝一半→还是两盒→先别执行 | 算法数量正确；同任务/草稿修订更新；保持待确认不取消 |
| 开封/部分和全部丢弃 | 日期、单位、来源及预览正确；开关关闭明确不可执行；不伪造消费 |
| 假设喝一半 | 只读算术，明确假设，无草稿/消费事件 |
| 同商品多批、同名不同商品、单位冲突 | 不按名称自动合并；冲突量null并保留原批次 |
| 待购来源未知/清单缺失/消费覆盖不足 | 正确原因和未知态，不显示零待购/零消费或确定耗尽日 |
| 来源PATCH设置/替换/清空、版本冲突 | 三义正确，同operation恢复原结果，不覆盖他人更新 |
| 建议依据任一维变化→确认/重验 | stale/blocked正确，自动规划仍不可提交，不拿诊断当授权 |
| 理解后/核对后/表达时中断、重启 | 保存计划恢复零模型；表达失败草稿不丢；未知结果不自动重试 |
| commit响应丢失→重进窗口→查回执 | 原operation恢复，一次库存/事件事务，不重复扣减 |
| 已成功但刷新/反馈失败 | 保留真实成功，提示刷新，不重新执行 |
| 两设备并发改口与确认 | 旧修订冲突，不自动改ID重发，不覆盖新决定 |
| 跨家庭/用户、换家庭、重登、权限撤销 | 最新权限检查，历史与引用不串用 |
| 新任务/新会话、过期、删除、终态批次 | 边界分别正确，旧历史不能延长引用或恢复终态 |
| 新版本上线后恢复P8.4旧请求 | 走原协议/记录，原结果与调用审计不被改写 |

最终分别签收：AI能力与契约、后端P8.5适配、前端承接、联合验收、实际发布。AI当前本地全量1,082通过/1跳过、后端旧兼容33通过、整改后240轮模型回归不能替代上述三方验收；首次独立保留组未达标的事实与后续回归区别见[P8.5评测记录](../versions/V1-P8.5/评测记录.md)。

**“一次完成三版对接”的完成定义：所有已开放能力走统一链路，全部未开放能力有准确降级，恢复和执行无重复，目标契约与实际导出一致，并有三方场景证据。它不意味着本次顺带实现长期偏好、向量库、Jev、多Agent、自动采购事务或新业务表。**
