### FE-01：聊天入口接入新版会话协议

**缺口证据：** 当前 [AgentClient.kt](../../frontend/app/src/main/java/com/example/teamapp/data/AgentClient.kt) 仍调用 `POST /api/v1/agent/conversation-messages`；[AssistantStore.kt](../../frontend/app/src/main/java/com/example/teamapp/data/AssistantStore.kt) 仍按旧登录会话绑定活动任务，尚未保存新版 `conversation_id` 和会话修订。

需要实现的调用顺序：

1. 打开助手，先 `GET /api/v1/agent/conversation?household_id={家庭ID}&limit=20`。
2. 只有返回 `requires_reset=true` 且没有会话 ID 时，才调用 `POST /api/v1/agent/conversation/reset` 初始化。持久保存本次重置的请求 ID。
3. 保存 `conversation_id` 与当前会话修订；新消息使用 `POST /api/v1/agent/conversation-turns`。
4. 请求只传家庭、会话 ID、会话修订、`request_id`、`text`，以及契约允许的可选成对 `task_id/revision`。不上传本机拼接的可信历史、库存事实或执行状态。
5. 响应的 `kind=task/clarify` 更新对应任务；`explain/needs_input` 展示解释或询问，保留返回的活动任务，不能把待确认草稿替换掉。
6. 分开维护会话修订、任务修订、草稿修订。恢复旧消息后，以 `current_conversation_revision` 或重新 GET 的修订作为下一次发送依据。409 时刷新并提示核对，不能自动换新请求 ID 重发旧动作。

**迁移约束：** 新旧协议不能仅替换 URL，因为请求和响应结构不同。切换新版后，旧消息不得自动混入新会话。现有详情页“询问这批”和 `sendForBatch()` 使用的旧 `reference-messages` 也要核对迁移：暂保留独立旧任务入口，或与后端约定可信引用桥接；不能向新消息请求擅自添加 `batch_id/reference`，也不能把两套活动任务绑定混用。

**验收：** 查询两批牛奶 → “第二批在哪里” → “把它移到冷藏室” → 生成正确草稿 → “为什么还没移动”，仍保留原待确认草稿，并解释尚未执行。这里只完成接入，执行仍走原有确认接口。

### FE-02：历史、恢复、身份隔离及新会话入口

**当前已有：** 本机保存任务、原请求和执行回执。**尚缺：** 按后端会话恢复最近 30 天历史、跨登录恢复当前会话，以及新版按请求 ID 查询理解结果。

前端工作：

- 按服务器、用户、家庭隔离缓存。重新登录后使用新令牌 GET 对应家庭当前会话，不凭旧登录 Token 恢复活动绑定。
- 历史按 `next_cursor` 向前分页，合并去重且保持顺序；历史状态只作为历史展示，当前状态读取 `active_task` 和最新执行结果。
- 发出消息前持久保存原请求 ID、完整请求体。超时、重建后先 `GET /api/v1/agent/conversation-turns/{request_id}?household_id={家庭ID}`。
- `completed` 恢复结果；`processing` 显示处理中并查询；`prepared` 仅按原请求恢复；`result_unknown` 显示待核实，不能生成新 ID 自动重发。具体行为遵守服务返回的恢复提示。
- 增加独立“开始新会话”入口，保留已有“开始新任务”。新任务保留本段聊天；新会话重置记忆，不取消旧草稿，不删除业务任务。
- 切换家庭、退出账号立即隐藏旧活动绑定；权限失效停止读取，不能残留其他用户或家庭的消息。
- 展示 `filled_fields` 以恢复输入；`truncated=true` 时提示上下文有限，不宣称无限记忆。30 天外的内容不在当前聊天读取范围。

**验收：** 关闭窗口、进程重建、退出再登录均可在权限有效时恢复；两台设备修订冲突不会覆盖；失败不重复模型请求或业务提交；开始新会话不误取消旧草稿。

### FE-03：已有采购来源的修改与清空

**缺口证据：** 当前 [CloudStore.kt](../../frontend/app/src/main/java/com/example/teamapp/data/CloudStore.kt) 的 `saveShopping()` 只在新建时提交来源；[CloudShoppingItem](../../frontend/app/src/main/java/com/example/teamapp/data/CloudApi.kt) 尚未保留 后端来源编辑需要的版本摘要。

接口：`PATCH /api/v1/households/{household_id}/shopping-list/items/{item_id}`。

- DTO 保存读取结果中的 `version`，它是 **64 位字符串摘要**，不是库存整数版本。
- 编辑界面提供保留来源、改选本家庭真实批次、明确清空三种语义：省略字段保留；UUID 设置；JSON `null` 清空。不能用空字符串表示清空。
- 提交来源变更时必须同时传稳定 `operation_id` 和读取到的 `expected_version`，结果未知时保留原请求。
- 来源必须与名称、规范化单位及生命周期相容；已购项目不能继续修改来源。冲突后重新读取，保留编辑意图，要求用户重新核对。
- 展示“来源未关联，建议可能不完整”，不能按同名自动关联或把未知待购当零待购。

**验收：** 设置、替换、清空、普通编辑不改来源均正确；跨家庭拒绝；两个成员并发只接受有效版本；延迟重试旧请求不会覆盖后来的新关联。

### FE-04：家庭成员操作摘要

**缺口证据：** 当前 [ConsumptionEventsPanel.kt](../../frontend/app/src/main/java/com/example/teamapp/ui/ConsumptionEventsPanel.kt) 对消费事件直接读取个人完整操作回执；同家庭其他成员的操作应使用已有受控共享摘要。

接口：`GET /api/v1/households/{household_id}/operations/{operation_id}/summary`。

- 自己的完整回执继续使用原操作接口；家庭流水中其他成员的操作展示共享摘要，不能要求后端开放别人的私人任务或聊天历史。
- 展示操作者、动作、时间、事件和允许的前后值。摘要与完整回执使用不同 DTO，不套用完整回执的结构或身份校验。
- 对普通 CRUD 产生、没有 DraftOperation 的新账本事件，直接展示账本本身，不假设每条事件都能请求草稿操作摘要。

**验收：** 同家庭能查看允许共享的业务事实，跨家庭拒绝；不能从共享摘要恢复他人私人对话或代其确认。

### FE-05：执行后只读反馈

接口：`POST /api/v1/operations/{operation_id}/feedback`。

当前助手在确认后读取回执和刷新库存，但尚未调用此反馈接口。前端应在已核实成功回执后提供“查看更新后的分析”入口，按需读取，避免重复自动请求。

- 分开显示业务执行结果和 AI 反馈状态 `available/partial/unavailable/not_applicable`。
- 反馈失败只提示分析暂不可用，业务仍已执行；不能再次提交原库存动作。
- `PLAN_ADD` 当前返回 `not_applicable`，正确表达为“已加入待购，尚未购买或入库”。采购专用分析需等待 AI／后端新契约，不伪造库存版本或反馈。

**验收：** 成功后 AI 不可用、网络失败或资料不足，均保留成功回执；重新查看反馈没有第二次库存或采购写入。

### FE-06：完整库存账本与更正

接口：

- `GET /api/v1/households/{household_id}/inventory-events?batch_id={批次ID}&limit=100&offset=0`。
- `POST /api/v1/households/{household_id}/inventory-items/{item_id}/corrections`。

现有消费流水只展示 Consumed，继续保留；另在详情提供“库存变更记录”，承接 `inventory-ledger-1`。

- 展示事件类型、精确数量、前后值、操作者、时间和关联事件；使用返回的 `next_offset` 分页并按事件 ID 去重，不沿用消费流水的字段假设。
- 区分消费、丢弃、调整、盘点、购买、归档和更正，不能将扣量都标为消费。缺失数量不补零；旧普通 CRUD 未完整回填需如实说明。
- 更正界面要求明确选择原事件、填写核对后的当前绝对数量与原因，提交稳定 `operation_id`、`expected_version`、`related_event_id`、`quantity`、`reason`。
- 更正后刷新库存、账本和规划资料，展示可能失效的原日期记录证明。保留原事件。
- 更正不是撤销事务、不是删除历史，也不支持擅自恢复终态批次；不新增后端没有的“撤销所有操作”按钮。

**验收：** 更正/盘点不增加消费总量；重复请求不二次调整；冲突后不覆盖其他成员；原事件与更正关系可查。

### FE-07：商品身份与批次归属

已提供的写接口：

- `POST /api/v1/households/{household_id}/products`。
- `PUT /api/v1/households/{household_id}/inventory-items/{item_id}/product`。

前端尚无相应调用。可以在现有详情或资料页面加入身份展示、创建并关联、显式解除关联。

- 创建使用稳定客户端 UUID、名称、基准单位和核对来源；规格、分类和标签按公开 DTO 填写。
- 关联提交稳定 `operation_id`、当前 `expected_inventory_version`、明确的 `product_id` 或 `null`，以及 `source`。
- 同名不自动合并；家庭确认标记不解释为平台审核通过。关联变更会更新库存版本，旧草稿应重新核对。

**读取依赖：** 当前后端路由已提供创建和关联，但未见公开商品目录列表接口。规划聚合位于内部 `provenance`，不能让手机直接调用内部规划接口取目录。完整的跨设备“选择已有商品”及聚合展示，需要先与后端确认公开目录／详情读取契约；不能仅靠本机缓存或让用户填写 UUID 作为完整交付。

**验收：** 同名不同规格不误合并，解除关联不删除库存批次；跨家庭商品不可关联；单位不兼容时不猜包装换算。

### FE-08：AI 库存兼容性诊断

接口：`GET /api/v1/households/{household_id}/inventory-ai-compatibility?limit=50&offset=0`。

当前已有本地单位和名称等校验，但尚未承接服务器诊断。建议在助手读取失败或库存资料入口提供“检查不兼容记录”，展示具体批次、字段和原因，跳转现有编辑页。

**验收：** 按 `next_offset` 读完后才可说明整体结果；`page_compatible=true` 只说明当前页。禁止自动改单位、猜容量或覆盖旧记录。

### FE-09：等待 AI 适配的规划扩展

这部分不是单纯前端缺按钮。AI 尚需读取后端新增的商品聚合、待购关联状态及新 `planning_basis`；前端当前可先完成布局和错误处理设计，最终按确认后的公开结果 DTO 接入。

- 保留现有批次级统计及缺口提示。只有获得已适配的公开结果后，才展示商品级跨批次规划。
- 区分登记总量、未过标签日期的活动量与经核实可用量；后者未知时不显示为前两者。
- 待购来源不完整时展示未知及修正入口，不能显示 0。
- 已有 `POST /api/v1/drafts/{draft_id}/planning-revalidation` 仅作诊断；`stale/blocked` 和 `PLANNING_BASIS_STALE` 应提示重新读取／生成，不允许前端替换依据字段强行确认。
- 当前 `automatic_planning_commit=false`、`manual_plan_only=true`。继续保留独立的明确数量手工采购入口；不能把计算建议改名成手工输入以绕过阻断。

**依赖与边界：** AI 负责新结果与依据适配；AI／规则负责人负责真实人工审核；后端负责审核规则同步及未来事务内重读、重算、提交。前端不能自行开启自动补货，也不能用补齐标签代替平台规则审核。

## 4. QA-01：联合验收清单

使用专用测试家庭和经授权的数据，验收最新构建的 APK。前端内存夹具、后端固定草稿测试、一次模型查询各自只能证明对应部分，不能互相代替。

| 场景 | 必须满足 |
| --- | --- |
| 查询牛奶 → 第二批位置 → 移动草稿 → 状态追问 → 确认 → 刷新 | 批次始终正确，追问不丢草稿，只有正式回执显示已执行 |
| 澄清／提交前关闭窗口、进程重建 | 找回原任务和已填字段，不重复理解或创建草稿 |
| 提交成功但响应丢失 | 查原操作恢复；相同操作 ID 一次业务效果 |
| 退出再登录、换家庭、两台设备、权限撤销 | 按当前权限恢复，会话和家庭隔离，修订冲突不覆盖 |
| 新任务与新会话 | 作用分别正确；不自动取消旧草稿 |
| 六类动作及全部数量模式 | 开封、移动不要求数量；全部消耗／丢弃数量来源和编辑保护正确 |
| 采购来源设置／替换／清空与延迟重试 | 来源和版本正确，旧回执不覆盖新关联 |
| 他人消费摘要、普通变更账本与更正 | 不泄露私人任务，不将调整／更正计为消费 |
| 执行成功后分析失败 | 成功状态保留，不触发再次写入 |
| 引用过期、库存变化、对象删除、长历史 | 重新核对；不将旧事实当最新库存，不改候选顺序掩盖失效 |
| 规则缺失、记录不完整、待购关联未知 | 明确不可用原因，不伪造零消费、耗尽日期或安全结论 |
