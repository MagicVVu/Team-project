# V1-P3 开发规划与实施基线

日期：2026-10-15。该规划经用户授权后已完成 AI 侧实现，当前策略 p3-policy-1；实测见 [交付记录](delivery-and-validation.md)。后端新增数据接口仍是提议契约，须双方验收；不能将 AI 实现视为真实预测上线。以下保留设计依据和依赖关系，具体已实现字段以 [AI OpenAPI](ai-openapi.json)、[上下文规范](planning-context.schema.json) 及 [后端协作](backend-coordination.md) 为准。

## 1. 当前基线与阶段目标

P1 已实现生命周期草稿及结构化续接；P2 风险工具和本地规则已实现，代码已按模块同步至服务器，独立环境及后端公开 HTTP 检查通过。本地回归 170 项通过。P2 正式容器切换、真实用户正向链路、风险字段接入与人工规则审核仍待完成，不能视为完整 V1 已验收。

已核对的后端 v0.6 能保存 AI 任务、结果、上下文和待确认草稿，但尚未提供确认写入、可靠库存事件、撤销及消耗历史只读工具。P3 设计和算法可先推进；对真实用户展示耗尽估计，需要后端事件与数据质量达到条件。

P3 目标是让用户能问清楚“记录了多少消耗”“按这些记录大约何时需要补货”“为什么建议买这个、买多少”，并得到可核对的依据。LLM 负责理解问题和选择工具；统计、预测、数量及理由由事实、明确偏好和确定性算法产生。

## 2. 建议冻结的范围

| 能力 | 示例 | 输出 |
|---|---|---|
| 消耗统计 | 过去两周记录了多少牛奶消耗 | 有效数量、单位、时间范围、事件数、排除项与完整性 |
| 耗尽预测 | 按现在记录的速度，牛奶还能用多久 | 参考天数/日期、日均记录消耗、观察窗口、条件与质量说明 |
| 补货建议 | 家里需要补什么 | 只读建议列表，区分阈值依据和历史消耗依据，列出已有待购项 |
| 单项采购草稿 | 给牛奶生成一份补货草稿 | 一个可编辑 PLAN_ADD 草稿、建议依据、当前快照，尚未写入 |
| 选择澄清 | 同名商品实际不相同或单位冲突 | 展示商品候选，由用户选择，不自动合并或选择第一项 |

不纳入：电商下单、自动写购物清单、后台主动采购、价格优化、复杂机器学习、家庭个性化长期学习、What-if、语音、图片、RAG、多 Agent 拆分。药品剂量推算和自动药品补货不属于本阶段。

只读查询可以返回多个商品的统计/建议；生成草稿仍一次一个商品、一个 PLAN_ADD 动作。当前前端的多项补货确认示意不构成批量执行授权。

## 3. 数据和事件口径

### 商品与批次

预测基于家庭内明确的 `item_key` 或稳定商品标识，汇总其多个批次。批次 ID 仍用于库存事实与版本校验。不能仅凭名称把不同规格商品合并，也不能把每个批次都当成独立采购需求。

仅自动换算当前已有的相容单位（g/kg、ml/L）。盒、瓶等包装容量不得猜测；商品容量/采购包装映射未经业务登记时，不跨包装换算。金额或数量不通过浮点数计算，沿用 Decimal 和字符串序列化。

最低库存沿用现有页面概念，但后端需要明确它是商品级偏好，不把每批的 minimum 简单相加。没有可信最低库存配置时，不能根据品名生成默认需求。

### 有效消耗

- 仅纳入已确认提交的 Consumed 数量；同一事件按 ID 去重。
- 排除 Discarded、Added、Opened、Moved、采购入库及未确认草稿。
- Finished 如果只是 Consumed 归零后的状态事件，不再计一次数量。
- 撤销和更正按明确的事件关联抵销或替换，不对所有负数量取绝对值；无法确定关系时返回需要核对。
- 迟录和回溯必须同时区分发生时间 `occurred_at` 与记录时间 `recorded_at`。回测只能使用当时已经记录的事件及撤销，不能利用未来录入或更正信息。
- 每次读取明确家庭、商品、时间区间、快照水位和完整性，不能截断分页后假称历史完整。

现有 Android `StockItem.history: List<String>` 是展示文本，不能解析成权威消耗账本；本机 Double 数据也不替代后端十进制事实。

### 质量与覆盖

区分“接口返回完整”与“用户实际消耗记录完整”。空事件不等于没消耗，零库存期间没有消费记录也不等于需求为零。后端需提供追踪起点、覆盖范围、已知断货/缺失区间及记录完整性来源；这些不能由 LLM 推断。

## 4. 首版预测方法

先做可解释的移动平均基线，不训练模型。建议初始策略版本为 p3-policy-1：最长回看 28 个完整家庭自然日，使用最近连续、明确覆盖且无未解释断货的有效窗口；当天未结束部分不进入日均速率的分母。

建议“可估计”门槛为：至少 14 个有效观察日、5 条有效消费事件、覆盖至少 3 个消费日期，且记录完整性、单位和事件关联可核实。这些是待评审的产品门槛，不是经真实用户验证的统计结论，后续应根据回测调整并保留策略版本。

基础计算：

```text
记录日均消耗 = 窗口内有效消费总量 / 有效完整观察天数
参考剩余天数 = 当前登记库存 / 记录日均消耗
参考日期 = 可信评估时间所在家庭日期 + 向上取整的参考剩余天数
```

结果明确条件：“未来不补货、消耗水平与所选记录窗口接近，按日期粒度估计”。日期不是精确耗尽承诺。

| 条件 | 处理 |
|---|---|
| 历史太短、记录覆盖未知或不完整 | insufficient_data，日期为 null，说明原因 |
| 完整有效窗口内没有消费 | no_recorded_consumption，不输出无限天或虚构日期 |
| 库存为零 | 展示“当前登记库存为零”，不制造未来耗尽日 |
| 同名不同商品、单位/事件冲突、断货影响未解释 | needs_review，列出候选或冲突 |
| 有合格窗口和正消耗速率 | estimated，返回公式输入、条件与快照 |

`estimated` 等属于 forecast 内部状态，AgentResult 保持原有五种状态。首版不输出未经校准的“90%可信”或统计置信区间；数据质量等级与统计概率分开。

P2 风险结果作为附带核对依据，不把丢弃当成消费，也不自动把风险/未知库存扣除后增加采购量。存在影响可用数量的风险或不确定事实时，补货建议降为 needs_review，待用户或业务流程核实。

## 5. 补货建议与草稿

建议分两条明确的依据：

1. **阈值建议**：有可信最低库存和当前数量时，可计算不足量，不依赖消费历史；标记 source=minimum_stock，不展示耗尽预测。
2. **历史建议**：预测达到条件，并有已保存的覆盖天数/采购提前量等偏好时，计算目标库存。缺偏好则要求设置，不能由模型补出采购周期。

候选公式：

```text
目标库存 = max(最低库存, 记录日均消耗 × (覆盖天数 + 采购提前天数))
建议新增待购量 = max(0, 目标库存 - 当前登记库存 - 已确认清单中的未完成待购量)
```

阈值分支只使用最低库存作为目标。未完成待购量用于避免重复建议，不能计入耗尽预测的现有库存。已购并自动入库的条目只计入库存一次；未确认 AI 草稿不当成已确认采购计划，不读取其他用户私有草稿来推断家庭需求。

待购读取失败、商品对应不明确或清单不完整时返回 needs_review，不把未知未购量当成零。已有未购量足够时解释“已有计划覆盖”，不再生成重复建议草稿。

采购单位、整包装及包装大小有明确业务依据时才能向上取整，否则保留原单位数量或要求核对。数量上限、精度和相容单位规则沿用现有服务，不能静默截断。

构造说明示例（非真实用户数据）：28 个有效观察日消耗 7 盒，日均 0.25 盒；现有 2 盒，参考约 8 天。若明确设置覆盖 14 天、提前 2 天，目标为 4 盒；清单已有 1 盒未购，则新增建议为 1 盒。没有这些明确偏好时，不直接生成该数量。

单项草稿沿用 PLAN_ADD 的 name/quantity/unit，增加独立的 planning_basis：商品、库存版本、清单版本、事件水位、策略、偏好版本、生成时间和计算依据。该依据需随草稿保存；仅保存在回复文本里不够。具体存储字段与后端确认服务一起冻结，不擅自给旧严格 Command 添加字段。

用户修改数量后标明人工修订，不能继续把修改值描述为算法原建议。最终加入共享购物清单由后端确认事务完成；确认前重读版本与未购量，变化时重新核对，不静默覆盖或双重添加。后端确认接口未就绪时仍只生成草稿。

## 6. 服务及接口设计建议

继续使用单 Manager：一次模型意图提取 → 只读上下文 → 确定性统计/预测/补货工具 → 模板解释或单项草稿。结构化候选选择不再调用模型，沿用身份、revision、有效期和重新读取机制。

AI 内部接口如下，现已在 P3 独立入口实现；后端代理和数据接入仍待完成：

| 接口 | 作用 |
|---|---|
| POST /agent/message | 复用 P1/P2，增加 QUERY_CONSUMPTION、QUERY_FORECAST、SUGGEST_PURCHASE |
| POST /agent/clarification | 兼容旧上下文，新增版本化商品选择上下文 |
| POST /consumption/query | 确定性统计，不调用模型 |
| POST /forecast/evaluate | 指定商品的耗尽评估，不调用模型 |
| POST /procurement/suggest | 建议模式可读列表；draft 模式必须限定单个商品 |

结果保留 trace_id、原文、五种处理状态与只读标志，新增 consumption_summary、forecast、recommendations、planning_basis。日期/速率/数量必须能回溯到工具事实、明确偏好与策略版本。

后台建议新增只读 `GET /internal/v1/planning/context`（待双方冻结）。目标是一次得到同一快照下的商品/库存、有效历史或可核验事件、覆盖与质量、共享清单未购项、明确偏好及各版本。数据量大时返回完整性和可续读游标，跨页保持快照；不能静默裁剪。后端可选择专用只读查询实现，AI 不自行连 PostgreSQL。

若选择多个现有读取接口组合，必须定义一致性校验和冲突重读，不能把不同时刻的库存、消费与清单拼为同一预测。超过总截止时间则返回失败和已保留输入。

P3 商品选择需要 `item_key`，不能冒用 batch_id。当前 v0.6 答案白名单没有该字段，需后端仅对相应已保存上下文允许它。新请求字段要进入网关校验、转发和幂等指纹；planning_basis 要进入草稿持久化与确认校验。结果 JSON 可保留新增字段，不代表所有新协议已自动可用。

首次处理和续接继续分别覆盖模型及工具的 10 秒总截止时间，无自动付费重试；失败保留原文、已填字段与手动处理提示。P2 中发现的 error 任务续接限制需要同时协调，不能再次设计无法从后端恢复的上下文。

| 阶段 | 工作 | 依赖/退出条件 |
|---|---|---|
| P3-0 设计冻结 | 事件口径、商品标识、覆盖质量、偏好、结果与确认依据 | AI与后端共同确认，明确哪些是现有接口、哪些拟新增 |
| P3-1 消耗统计 | 模型、只读适配器、有效事件归并、单位和时区 | 合成夹具验证去重/撤销/Finished；真实统计需事件工具 |

| P3-3 补货建议 | 阈值/历史两条依据、未购扣减、单项草稿 | 共享清单/偏好读取就绪；确认闭环依赖后端事务 |

P3-0/1/2 的设计与算法开发可在 P2 联调期间并行；真实预测上线不能跳过确认/事件/撤销和数据完整性验证。不承诺日历工期，先按上述依赖估算工作量。

服务器实现建议放在 `~/workspace/agent/p3/` 的 schemas、history、forecast、procurement、tools、manager、app；联调客户端仍在 integration。测试及评测源文件在本地仓库维护，必要测试代码可在同一服务器工作区运行。运行规则/策略文件可随 AI 代码同步，说明文档、OpenAPI 与报告只留本地仓库；不创建远端交付包目录，不放宽服务器权限。

交付包括 P3 服务、自动化测试、独立意图评测、算法案例、OpenAPI、字段/状态说明、后端协作清单及真实数据回测报告模板。没有真实数据时将效果报告明确标为未验证。

## 9. 验收与评测

- 新建 150 条意图表达，90 开发/60 保留，按场景组隔离，标明构造来源和人工复核状态；保留 P0/P1/P2 数据和结果。
- 算法夹具覆盖真实事件形状，但属于测试数据，不交付假库存/假事件服务，不作为预测有效性证据。
- 必测：重复消费、Consumed+Finished 双记、部分/全部撤销、更正迟录、丢弃不进消费、断货、缺失窗口、单位冲突、同名不同商品、多批次、已购入库防双计、已有待购、风险未知、超量、跨家庭、旧快照、过期/旧修订、超时和提示注入。
- 意图准确率目标 ≥90%，需要澄清场景召回率 ≥95%；统计、公式输入/输出、草稿字段及专项边界全部正确；所有 AI 路径不写库存/清单，结构化续接不调用模型。完整 AI 流程 P95 目标 ≤10 秒，分别测规则与真实模型及服务器环境。
- 真实预测采用时间顺序回测：历史截断后预测，禁止未来事件泄漏。新增采购、丢弃或未解释调整改变耗尽过程时，标记干预/删失，不拿该区间当未受干预的耗尽标签。
- 建议积累至少 30 个可核验、未受干预的真实耗尽区间后，再报告 MAE、绝对误差中位数、覆盖率和不出预测的比例；同时与简单基线比较。数量是评测设计建议，不是当前已有样本。绝对误差上线门槛待真实基线后冻结，不用合成数据宣布“预测准确”。

本轮已完成 AI 侧代码、测试、独立模型与规则评测、契约及代码白名单同步；未修改前后端、未切换正式容器、未提交或推送。真实账本、确认事务、人工复核及真实效果验收仍待完成；多 Agent 拆分仍留在 V1.5。
