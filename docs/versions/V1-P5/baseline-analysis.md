## 3. 同一路径下存在两套不兼容的网关协议

| 项目 | 仓库本地 backend/app.py / Android 客户端 | 远端正式后端 v0.6.0 |
|---|---|---|
| 消息路径 | POST /api/v1/agent/messages | 同名路径，但请求/响应语义不同 |
| 请求事实 | text、request_id、inventory_revision、items | household_id、text、request_id、household_timezone |
| 身份 | APP_API_TOKEN、固定本机快照作用域 | 业务登录用户与家庭成员权限 |
| 库存权威来源 | 手机上传快照 | 后端数据库及只读库存工具 |
| 返回/恢复 | expected_revision、engine、data；当前客户端候选只保留ID | task_id、任务revision、结果及草稿引用；按任务查询/澄清 |
| 草稿处理 | POST /api/v1/agent/drafts/validate，校验后计划在手机应用 | 当前公开的是 GET /api/v1/drafts/{draft_id}，未见同名validate或确认路由 |

不能只改 baseUrl 就把旧客户端指向服务器；也不能把 APP_API_TOKEN、AI_SERVICE_TOKEN、BACKEND_TOOL_TOKEN 混为用户登录令牌。

建议 P5 的在线模式以正式后端为库存、清单和任务的权威来源，手机发送用户确认文字并展示结果；本机游客模式继续明确标识为本机记录，不能在失败时悄悄切换写入来源。不在本轮自动迁移或合并用户既有本机库存，迁移须另有可核对的方案。

当前 AgentCommand 强制所有动作有 quantity/unit，且仅应用 ADD/CONSUME/PLAN_ADD；无法表示无需数量的 OPEN/MOVE，以及 DISCARD 的模式字段。AgentReply 仅保留候选ID，没有完整候选事实、任务恢复和 P3依据。P5 接入前须按 action 分型，或显式限制可用能力，不能解析失败后套用旧模型。

## 5. 对 P5 的结论

下一阶段有价值的增量是把已有语音转写接到经过修复、身份和事实来源明确的文字草稿链路。优先工作并非再写一套语音解析器，而是修复发布一致性、统一任务协议、保留识别与用户修订证据，并处理重复回调、取消和断线恢复。

语音实现可先做单物品、单动作，使用设备现有识别服务；已核对文本只提交一次。P2/P3 由后端数据能力控制开放，不能把所有历史接入缺口同时强行算进语音首版。多 Agent、复杂长期记忆和自动下单不纳入 P5。
