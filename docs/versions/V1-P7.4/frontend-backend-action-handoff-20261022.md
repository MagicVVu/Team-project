# V1 当前前后端待办与 AI 接入交接

日期：2026-10-22，Asia/Shanghai。供 Android、后端和 AI 成员共同使用。

本文件以本日刚完成的服务器检查、发布证据和本地源码为基线；不代表已重新执行一次手机端完整验收。后续版本发生变化时，应以实际部署接口和新验收结果更新状态。

## 1. 当前基线与分工

- 正式后端：`0.9.0`，镜像 `magicvvu/backend:households-20261022`。
- 正式 AI：DeepSeek 引擎，P7 协议；本地 P7.3 改进和 P7.4 取消费率日期拦截已发布，镜像 `magicvvu/agent:p74-6630097c1f56`。
- 当前源码的日常 Debug 包：`1.1-test`，versionCode 2，默认连接共享 HTTPS。最近一次检查的 MuMu 仍安装 `1.0`、versionCode 1，不能用旧包页面判断新代码是否生效。
- 已有登录、家庭共享、库存和采购功能，已有 AI 任务网关、确认页面、执行回执和恢复代码；继续复用，不替换数据库任务网关、不新建 Mock 服务。
- AI 负责理解原文、判断缺字段、生成草稿与计算建议。权限、任务存储、最新修订、确定性校验、正式执行、幂等、业务事件及回执归后端；页面展示、编辑、交互与恢复入口归前端。
- 目前正式执行能力：`ADD / MOVE / PLAN_ADD / CONSUME = true`；`OPEN / DISCARD = false`。可信引用和自动规划提交均未开放。

**本轮协作目标：先把已有四类可执行动作在最新版 App 中跑通，再补齐续接、引用、开封、丢弃和规划数据。AI 返回草稿不等于操作已完成。**

### FE-02：主聊天框承接续接和引用（T03、T04）

当前 `CloudAssistant.kt` 只对前三个简单序号作特殊处理，并主动拦截部分“它”表达。已有 `ClarificationReplies.kt` 不等于主输入框已完整接入续接。

需要实现：

- 明确保存“当前活动任务”，不能始终取聊天列表最后一条代替当前任务；用户换话题时新建任务，旧记录仍可查看。
- 用户输入先按双方确定的零模型路由契约处理，保持原文，不偷偷拼接物品名；无法唯一确定缺失字段时继续询问。
- 允许字段来自当前任务 `allowed_fields`，候选来自同一修订；不能默认第一批，不能使用旧修订的序号。
- 查询后引用只关联后端可核实的来源任务和明确选择。不能提交历史数量、位置、版本作为可信事实，不能直接创建内部 `reference`。
- 后端适配层尚未开放时，继续提示重新选择或写明物品；不要先删除“它”的保护提示，再把未绑定指代直接当作新名称发出。
- 接通后覆盖“它在哪”“它在什么地方”“这批放在哪里”“就第二个吧”“两盒”“昨天”“开始新任务”。
- 切换家庭、退出账号或明确开始新任务时清除活动引用；持久历史与当前活动对象分开管理。

### FE-03：确认表单、状态和恢复（T02、T05、T06、T10）

- 继续保存完整结果、`request_id / task_id / revision / draft_id`，以及确认时的稳定 `operation_id` 和原请求体。
- 展示正在处理、需要补充、待确认、提交中、已执行、失败、结果待核实；只有可核实正式回执才能展示已执行。
- 草稿显示目标批次、预期版本、字段来源和变更前后；编辑内容不能把历史预览伪装成重新计算后的确定结果。
- 开封表单只要求开封日期，不要求数量；移动只要求目标位置，不要求数量，也不扩展部分移动。
- 丢弃展示 `discard_mode=partial/all`。全部模式的数量来自当前批次，不能伪装为用户输入；模式/动作切换不属于普通九字段澄清，应按正式契约重新生成和核对草稿。
- 修改动作或目标批次时重新生成草稿；仅允许编辑后端声明可编辑的业务字段。
- 能力未开放时显示待确认/暂不支持及准确原因。手动页面也缺少对应业务能力时，不能建议用户改数量或删除记录来冒充开封、丢弃。
- 确认响应丢失时先查原任务/回执；恢复提交沿用原操作 ID 和完全相同请求。404 不能单独证明从未执行。
- 已执行但刷新失败时保留成功回执，提示重新刷新，不允许再次执行同一操作。

### FE-04：统计、建议和家庭管理（T07～T09）

- 对统计/预测/建议，展示数据时间、依据、缺失字段与原因码；无数据不能显示“消费为零”或猜测耗尽日期。

## 4. 后端具体工作

### BE-01：先恢复可发布源码（T01）

以下本地文件仍有合并冲突标记，应先解决冲突、排查重复路由并跑回归：

- `backend/server/app/execution_schemas.py`
- `backend/server/app/routers/agent_gateway.py`
- `backend/server/app/services/planning_context.py`

服务器当前镜像的前两份文件语法正常，第三份尚不存在。本地有冲突代码或某个预留模块，不代表正式环境已支持；不要直接整体覆盖运行目录。部署前以当前运行镜像及已发布的家庭/密码规则为基线，避免回退队友刚完成的功能。

### BE-02：接入续接及可信对象引用（T03、T04）

复用 AI 已实现的 `conversation/replies.py`，具体行为和样例见 [P7.3 续接交接契约](../V1-P7.3/frontend-backend-handoff.md)。它是调用方纯函数，不是已经向 Android 提供的文字续接 HTTP 接口。

1. 从数据库按当前登录身份读取任务，核实用户归属、家庭成员关系、任务状态、最新修订和有效期后，构造可信 `BoundTask`。
2. 以家庭/原任务保存的 IANA 时区及可信时间解释日期；不能把手机日期当作可信当前时间。
3. 路由结果严格区分 `clarify / new_task / needs_input / clear_reference`。合法澄清转成原接口的 `revision + answers`；继续询问不得新建付费请求。
4. 保留公开消息四字段和澄清九字段约束，原文完整保存。答案不能修改动作、家庭或库存版本。
5. 为现有 `POST /api/v1/agent/reference-messages` 预留能力提供真实实现；该路径当前为固定不可用，不能仅修改能力标志。
6. 对象引用由后端核实并生成，包含已认证作用域、来源任务/修订、真实批次、签发及到期时间；最长 15 分钟。只有对象唯一或用户明确选中时可发起引用。
7. 续接、引用与确认均重新核对当前家庭权限；引用不能因重新打开窗口而从旧缓存自动续期。AI 会重读批次事实，不接收手机历史事实替代工具结果。
8. 处理被删除/终态批次、库存变更、过期、修订冲突和跨家庭访问，返回可供页面采取行动的原因。

不要把 AI 的 `BoundTask` / 内部上下文原样暴露给手机；手机的 `household_id` 也必须与已认证成员关系核对。

### BE-03：补开封、丢弃的正式执行（T05、T06）

复用现有草稿确认、幂等与回执框架。是否新增手动业务入口由后端按现有架构决定，先提供准确契约，不让前端猜路径。

| 动作 | 必须落实的业务语义 |
|---|---|
| `OPEN` | 有效活动批次、明确且不在未来的开封日期；数量不变；已有开封事实不重复修改或重复生成事件 |
| `DISCARD partial` | 正数数量、兼容单位、不可超量；扣减数量，独立记录丢弃事件；扣至零时采用明确一致的终态规则 |
| `DISCARD all` | 以当前批次数量为依据，核对草稿预期版本；数量归零，记录 `DISCARDED` 终态及丢弃事件；版本变化要求重新核对，不能静默扩大丢弃量 |

共同要求：

- 在事务中验证权限、批次状态、版本、字段、单位和操作 ID；保存执行结果、业务事件和可恢复回执。
- 核对并按需迁移现有动作/事件 CHECK 约束、DTO、可编辑字段和终态转换；不能只增加一个路由或把能力改为 true。
- 库存数量最多六位小数，采购数量最多三位；保留既有精度与长度约束，不截断或擅自取整。单位换算使用确定性规则。
- 全部丢弃与消耗事件分开，丢弃不计入消费速率；通用数量调整不能自动当成消费。
- 重复请求复用原回执，不重复扣减、不重复记事件；编辑受保护字段或复用操作 ID 发送不同请求应拒绝。
- 接口、迁移、回归和联合验证准备就绪后，再逐动作开放 `execution-capabilities`。

### BE-04：补齐规划数据读取（T07、T08）

当前正式服务未注册 `GET /internal/v1/planning/context`。AI 消费统计、耗尽预测和补货建议实际返回 `PLANNING_CONTEXT_UNAVAILABLE`，这是当前主要数据缺口。

直接对齐已预留的 V1 契约，参考 [规划数据 Schema](../V1-P6/planning-context.schema.json) 与 [AI 读取实现](../../../agent/v1/tools.py)，不要另建同义接口。

| 数据 | 后端需要提供的事实 |
|---|---|
| 身份与快照 | 当前认证 scope、`snapshot_id`、`as_of`、`event_watermark`、`shopping_version` |
| 库存 | 真实批次、数量、单位、版本、日期、位置、状态和完整读取标志 |
| 消费历史 | 已提交事件的真实类型、发生/记录时间、数量单位及关联；区分消费、丢弃、调整、撤销/纠正 |
| 记录覆盖 | 逐日完整性、缺货、无法解释的调整及完整性来源；无事件不等于记录完整或零消费 |
| 库存核对 | 可用库存是否被业务核实、核对时间与来源；不能把普通编辑时间直接当成用户盘点时间 |
| 偏好 | 有来源的最低库存、覆盖天数、提前期、订货单位/包装量及版本；未设置保持缺失 |
| 待购 | 当前共享待购、确认状态、单位、完整性和版本；未读完不能声明无重复采购 |
| 风险事实 | 有来源的标签日期/类型、商品分类、开封情况、储存条件；未知字段保留未知 |

AI 当前要求规划快照新鲜、物品读取完整；具体协议版本、必填项和校验以 Schema 为准。后端应准确表达缺失数据，不为“让接口通过”把完整性全部设为 true，也不要用历史通用扣减拼造消费事件。

仅有数据库 `opened_at` 字段、消费事件列表或最低库存字段，不代表整个规划契约已经实现。自动计算的补货提交还需业务重验机制；准备前继续保持 `automatic_planning_commit=false`，复用已有预留契约，不新建重复提交接口。

人工审核规则目前为零。后端提供事实与管理支撑，业务人员/AI 成员共同完成有来源的规则审核；不能用模型猜测代替审核。

### BE-05：维持执行边界和恢复能力（T02、T10）

- 现有 `CONSUME=true` 需验收正式消费事件及回执，不以直接数量扣减冒充完整语义；库存页手动调整是否属于消费也要明确。
- 任务、草稿、确认状态、操作 ID 与回执稳定关联；AI 返回草稿或用户点击确认均不直接产生已执行状态。
- 库存/草稿冲突不自动替换预期版本，必须重新核对；结构化澄清不得再次调用付费模型。
- 发布、读取、续接和确认均保留现有认证及家庭隔离，前端不持有 DeepSeek Key 或内部服务令牌。
- 对端超时后提供真实可查询结果；不要把客户端断线当作业务必然回滚。

## 5. 已上线家庭管理：前端可直接接入（T09）

下面均要求登录，前缀为 `/api/v1/households`。不是本次要求后端重新开发的功能。

| 方法与路径 | 请求 | 前端处理重点 |
|---|---|---|
| `POST /{household_id}/leave` | 无请求体 | 所有者须先转让或解散；成功 204 后切换家庭 |
| `DELETE /{household_id}/members/{user_id}` | 无请求体 | 所有者可移除非所有者；管理员只能移除普通成员 |
| `PATCH /{household_id}/members/{user_id}` | `{"role":"admin"}` 或 `{"role":"member"}` | 仅所有者可设置/取消管理员 |
| `POST /{household_id}/transfer-ownership` | `{"new_owner_user_id":"已有成员 UUID"}` | 仅所有者；成功后刷新自己和目标成员的角色 |
| `DELETE /{household_id}` | `{"confirmation_name":"当前完整家庭名称"}` | 仅所有者；先说明删除范围并要求精确输入家庭名称 |

退出/移除仅删除成员关系，保留家庭共享数据；解散会删除该家庭库存、采购、任务、草稿、回执和业务事件，不删除用户账号或其他家庭。成员/角色变化会使未用邀请码失效，前端应刷新提示。

详细权限、事务与错误码以 [家庭管理发布记录](../../../reports/household-management-20261022/README.md) 为准。

## 6. 双方接口与页面共同约束

继续使用已有公开接口：

- 普通消息：`POST /api/v1/agent/messages`
- 原任务澄清：`POST /api/v1/agent/clarifications/{task_id}`
- 任务恢复：`GET /api/v1/agent/tasks/{task_id}`
- 草稿读取：`GET /api/v1/drafts/{draft_id}`
- 执行能力：`GET /api/v1/agent/execution-capabilities`
- 草稿执行状态：`GET /api/v1/drafts/{draft_id}/execution`
- 用户确认/取消：`POST /api/v1/drafts/{draft_id}/commit`、`POST /api/v1/drafts/{draft_id}/cancel`
- 操作回执：`GET /api/v1/operations/{operation_id}`

可信引用路径虽然已预留，当前尚不可用。AI 内部 `/agent/message`、`/agent/clarification`、统计/预测接口不应由手机直接调用。新增适配协议须明确区分“设计中、已实现、已部署、已联合验证”。

状态对应关系：

| 事实 | 页面应展示 |
|---|---|
| 请求发送中 | 正在处理/提交中 |
| AI 要求补充 | 需要补充，保留原任务 |
| 有草稿但无正式执行回执 | 待确认，尚未写入 |
| 已提交但响应丢失/尚无可核实结果 | 结果待核实，提供原请求恢复 |
| 正式成功回执已核实 | 已执行；刷新失败另提示重新刷新 |
| 接口、权限或业务校验失败 | 失败/冲突/已过期等准确状态，保留原文和已填字段 |
| 后端能力或规划资料不足 | 暂不可用，显示原因；不能以零值代替缺失 |

## 7. 联合验收清单

主场景：“把牛奶移到冰箱” → 多批次候选 → 选择 → 前后草稿 → 用户确认 → 后端移动 → 正式回执 → 库存刷新。

必须使用最新目标设备版本和专用测试家庭，不在普通用户库存上自动执行测试写入。

- [ ] 新增、移动、消耗、加入采购计划分别走完页面确认和真实回执。
- [ ] 候选不默认第一批；“第二个”“就第二个吧”按同一修订顺序选中。
- [ ] “两盒”“昨天”只补当前允许字段；多个可能字段时继续询问；非法/未来开封日期被纠正。
- [ ] 换话题新建任务；开始新任务、换家庭或退出账号清除引用。
- [ ] 唯一对象可追问位置；多对象、过期、删除、终态和跨家庭引用不能错误承接。
- [ ] 库存变更触发重新核对，不自动改版本继续提交。
- [ ] 在澄清、提交前和提交响应丢失时退出/断网，恢复后不丢任务、不重复执行。
- [ ] 成功提交但刷新失败仍保留已执行回执。
- [ ] 开封/丢弃开放后，数量、日期、模式、终态和事件语义全部正确；开放前不能显示执行成功。
- [ ] 缺历史、缺核对时间、待购未读完整、偏好缺失时准确降级；充分数据时计算可复核。
- [ ] 前端显示的补货依据与按钮实际提交依据一致。
- [ ] 家庭权限变化后，旧任务、旧草稿、旧引用与缓存不能绕过新权限。
- [ ] 结构化续接零模型调用，首次理解最多一次，错误不自动付费重试。
- [ ] AI 全路径不写库存；真实写入只能经业务层确认执行。

分别登记“AI 已实现、后端已部署、前端已承接、联合验收通过”，每项填写版本、证据和待处理原因。AI 单元测试通过不代替页面验收；单次模型耗时不代替完整 AI 流程 P95 指标。
