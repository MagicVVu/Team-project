## 1. 必看的接口契约

| 文件入口 | 用途 |
| --- | --- |
| **[AI OpenAPI JSON](contracts/ai-openapi.json)** | 当前会话 AI 的完整请求、响应和认证契约，含 `/agent/message`、`/agent/clarification`、只读规划和 `/feedback/after-commit` |
| **[Backend OpenAPI JSON](contracts/backend-openapi.json)** | 当前本地正式业务 API，含新增摘要、归档、兼容诊断和反馈适配路由 |

JSON 定义为字段结构依据，本文补充作用域与流程语义。旧公开消息四字段、澄清九字段、六类动作及现有数据库任务网关保留。对象引用和本文新增的结果来源由受信任调用层处理，手机不能直接提交伪造的库存事实、任务结果或版本证明。

本地导出方式：在 `agent` 下运行 `python -m conversation.export_repair_contracts`；在 `backend/server` 下运行 `python -m app.export_assistant_contracts`。后者导出时替换为不连接数据库的引擎，不运行迁移。

## 3. AI 修复后的对象与草稿语义

### 3.1 指定批次查询

现有 `POST /api/v1/agent/reference-messages` 继续使用真实来源任务、修订号和批次 ID。后端核实后传给 AI；前端保持原文，不拼接物品名。

当前页面四条固定查询及“这批已经全部用完”由确定性代码处理，零模型调用；其他自然表达最多一次提取。每次都重新读取事实。未选对象、对象删除或终态会要求重新明确；过期要求重新选择；跨家庭拒绝；规划与库存不一致要求重新核对。

**批次与商品不得混用：** 本轮只修复选定批次的查询。后台若只提供多批次商品合计而没有批次独立历史，返回 `BATCH_PLANNING_SCOPE_UNAVAILABLE`。不能靠同名合并或截取合计中的一批来伪造单批次统计。

### 3.2 全部消费

AI 结果示意（省略其他正常字段）：

```json
{
  "status": "needs_confirmation",
  "quantity_source": "current_batch",
  "consume_mode": "all",
  "draft": {
    "action": "CONSUME",
    "name": "牛奶",
    "batch_id": "11111111-1111-4111-8111-111111111111",
    "expected_version": 4,
    "quantity": "2",
    "unit": "盒"
  }
}
```

前端读取 `/api/v1/drafts/{draft_id}/execution` 的 `editable_fields`，全部消费为 `[]`。确认请求 `edits={}`，不要把显示中的数量再次当成编辑提交。想改成部分消费时新建任务，不更改全部模式。后端从已保存任务结果验证模式，不相信手机传来的 `consume_mode`。

版本冲突时保留原任务和输入，让用户重新核对；不能悄悄将其他成员刚新增的余量全部扣完。

### 3.3 包装单位

示例：当前 2 盒、待购 1 盒、目标 20 盒，每包 6 盒，建议 3 包：

```json
{
  "current_stock": "2",
  "pending_quantity": "1",
  "target_stock": "20",
  "inventory_unit": "盒",
  "suggested_quantity": "3",
  "unit": "包",
  "order_unit": "包",
  "pack_size": "6",
  "pack_size_source": "saved_preferences"
}
```

前三个数量使用 `inventory_unit`，建议数量使用 `order_unit`（与旧 `unit` 同义）；换算展示为 `1 包 = 6 盒`。`pack_size` 仅在建议实际采用包装换算时返回，否则为 null。新字段位于当前结果的 `recommendations[]`，历史 `planning_basis.calculation` 保持旧结构，不能把其中唯一的 unit 套用到库存数量。

兼容旧服务器时，新字段可能缺失。无法从同一份已核实结果取得库存单位时应提示单位依据不足，不猜测、不统一加采购单位。

### 3.4 手动采购来源

可信批次来源的手动 PLAN_ADD 会额外返回：

```json
{"procurement_source":{"batch_id":"11111111-1111-4111-8111-111111111111","expected_version":4}}
```

它属于 AI 结果，和用户原文、草稿分开保存；不能由确认表单编辑。后端确认时复核家庭、批次活动状态、名称、版本及兼容单位，写入现有 `ShoppingListItem.source_inventory_item_id`。模型和前端均不能按同名自动关联。

无明确来源的新物品或旧草稿保留空来源。这仍可能使待购完整性不足，不能把未知待购当成零。旧来源的修改／清除、本质商品关联及包装采购事务由后端负责人进一步设计。

## 4. 本地新增后端读取接口

下列接口均要求现有 Bearer 登录。完整参数、响应结构及 UUID 类型见 Backend OpenAPI。

| 接口 | 用法与限制 |
| --- | --- |
| `GET /api/v1/households/{household_id}/operations/{operation_id}/summary` | 家庭成员可读正式业务摘要，含执行者 ID、事件、名称、数量、脱敏前后状态；不含 task/draft、对话、请求内容、账号资料和 history_json |
| `GET /api/v1/households/{household_id}/inventory-items/{item_id}` | 读取单批次，包含终态；不产生新操作 |
| `GET /api/v1/households/{household_id}/inventory-items?status=DISCARDED` | 显式状态筛选，可选 ACTIVE/FINISHED/DISCARDED/REVERSED/all，支持原有 limit/offset；不传 status 时仍为 ACTIVE/FINISHED |
| `GET /api/v1/households/{household_id}/inventory-ai-compatibility` | 分页定位不兼容记录及首个阻塞字段，返回批次 ID、库存版本、原因和手动建议；仅说明本页，不代表全家庭兼容 |
| `POST /api/v1/operations/{operation_id}/feedback` | 无请求体；原执行者在业务成功后请求只读 AI 反馈，不写库存／采购，不重放提交 |

消费流水新增 `actor_user_id` 和 `operation_summary_url`。前端“查看业务回执”应读取这个摘要 URL，不能继续要求其他成员访问原执行者的私人回执。原 `/api/v1/operations/{operation_id}`、私人任务和草稿的权限没有放开。

摘要只覆盖现有 DraftOperation/BusinessEvent 所记录的操作，不是全量业务时间线。归档详情只解决读回批次，前端历史入口和完整账本仍需分别承接。

兼容性诊断只报告问题，不自动把“箱”换成“盒”、猜容量、截断名称或隐藏坏记录。全部分页也没有跨页同快照保证；修复后必须重新查询，不能把某一页没有问题视作全家庭可用。

新增能力声明位于原 `/api/v1/agent/execution-capabilities`：`consume_all_protected`、`manual_procurement_source`、`household_operation_summaries`、`archived_inventory_reads`、`post_commit_feedback`。旧服务器可能没有这些字段，前端应按不支持处理。本轮 `automatic_planning_commit=false`、`manual_plan_only=true` 保持不变。

## 5. 确认、刷新与反馈的正确顺序

1. 获取 AI 结果，展示待确认草稿及真实目标批次。
2. 获取 execution 状态和允许编辑字段；沿用原任务、草稿、修订号。
3. 用户确认后提交原有 commit 接口，使用稳定 operation_id；超时先查询原回执，不能换 ID 重复提交。
4. 只有正式 committed 回执才能显示“已执行”；保存成功结果并刷新库存／待购。
5. 可独立请求 feedback 接口。它在请求 AI 前释放数据库连接，不自动重试，使用 10 秒总截止；只接受与原操作对应的只读反馈。
6. feedback 返回 unavailable、网络超时或刷新失败时，保留业务已成功提示。不能回滚提示状态、再次扣库存或重复加入采购。

feedback 响应区分 available/partial/unavailable/not_applicable，`business_committed=true` 表示已核实原操作成功。PLAN_ADD 返回 not_applicable，文案明确“已加入待购，尚未购买或入库”，不伪造不存在的 batch_versions。

| 核心设计项 | 当前限制及应明确的设计 |
| --- | --- |

| 撤销与纠错 | 定义最新可逆事件、权限、依赖、版本与幂等；追加更正／反向事件，不删除原事件、不把盘点差额算消费 |
| 补货执行事务 | 按确认时完整快照重算并校验库存、事件、偏好、待购等依据，保存原建议与人工调整；不能用手工标记绕过校验 |
| 采购来源修改／清除 | 设计版本／幂等规则、同家庭与单位检查、已购项限制、明确空来源语义及待购完整性边界 |
| 商品级规划证据 | 定义多批次 coverage、盘点和偏好如何有效聚合，归组变化如何使旧证据失效；单批次证据不能自动代表整个商品 |
| 审核管理持久化 | 如需后台审核、权限与审批记录，另行设计存储；本轮只有本地候选和校验，不是审核系统 |

规则负责人还需实际核实来源、适用范围、日期和商品关联，提供真实人工批准记录。本轮的候选与源链接保留历史来源记录，没有进行新的专业审核。CLI 的内容摘要和日期检查不能证明审核人身份；运行配置只应由可信负责人发布。

## 8. 联合验收与发布边界

最少验证：同名两批选其中一批做四种只读查询；全部用完在澄清、确认前发生库存变化；关联采购确认后待购抵扣；6 盒/包的单位卡片；A 执行、B 查摘要；全部丢弃后归档可读；盘点导航；成功后反馈超时；切换家庭、退出和 UNKNOWN 恢复。

测试证据见 [工作记录](工作记录.md) 及 [验证汇总](../../../reports/v1-local-chain-repair/verification-summary.json)。40 条合成离线回归不是模型准确率或线上性能验收。SQLite 通过也不代表 PostgreSQL 并发已验收。

本轮代码、测试和契约均在本地。部署 AI 与后端、前端承接、真实家庭数据验证和手机联合验收应分别记录。未审核规则、商品级聚合、完整账本、撤销及自动补货执行仍未完成，不能据此宣布整个 V1 全部覆盖。
