# Android 结果展示与执行恢复

2026-10-29，Asia/Shanghai。

## 用户能看到的变化

- 窗口顶部显示当前活动草稿，区分尚未确认、确认结果待核实、已经收到成功回执。
- 展示本轮任务和后端已校验 evidence 中的结构化结果，重复结果只显示一次，不把别的活动草稿当成本轮查询结果。
- 商品卡片显示登记总量、活动批次量、可用量、已记录消费小计、统计范围、待购量、耗尽参考和建议补货量；展开关联批次并进入资料核对页。
- 缺少数据时明确显示“未知 / 尚不足以判断”。没有消费记录不等于零消费，待购来源不完整不等于零待购。商品汇总和批次数量不重复相加。
- 显示待购来源状态、资料缺口及补录入口；将常见原因转换成中英文说明。
- 候选显示批次版本；过期候选不能继续选择，提供核实恢复入口。草稿版本或任务版本变化后，清除旧编辑、旧预览和旧建议核对结果。
- 自动补货建议可点击“重新核对建议依据”，展示依据已变化或仍缺少资料。沿用后端限制，自动补货不能直接提交；仍可在采购页明确输入手动数量。

## 防止重复执行

同一份草稿在不同聊天消息中出现时，共享已经持久保存的确认请求、operation_id 和经校验的回执。连续点击或多个入口确认时不产生第二个新的操作编号。

确认 POST 丢失响应时先 GET 原 operation_id 的执行记录。找回成功回执就显示已执行；即使库存刷新失败，也保持已执行，不再扣减。404 不能证明没执行，保持原请求待核实；只有用户明确恢复时，先查询，再使用完全相同的操作编号和请求内容恢复，版本变化则阻止重交。

回执继续验证协议、用户、家庭、任务、草稿、动作、原请求修订和操作编号。普通聊天、结果卡片、预览和建议依据核对都不产生库存写入。

旧版持久请求继续按自己的原请求恢复；即使同一旧草稿保存过不同确认内容，也保留每份原始记录并允许分别查询回执，同时阻止再次提交和相互覆盖。Android 使用的公开会话接口不直接选择 AI 的 P8.4/P8.5 阶段协议，服务端历史协议恢复保持原有实现。

## 改动位置

- `frontend/app/src/main/java/com/example/teamapp/data/AssistantResults.kt`：结构化结果收集及去重。
- `frontend/app/src/main/java/com/example/teamapp/data/DraftConfirmations.kt`：同一草稿的确认记录共享、旧冲突记录保留。
- `AssistantModels.kt`、`AssistantStore.kt`、`AgentClient.kt`：持久化、先查回执、固定原请求恢复、建议依据核对接口。
- `ui/CloudAssistant.kt`、`ui/AgentResultCards.kt`、`ui/AlignmentUi.kt`：当前草稿、商品和资料卡片、候选状态与恢复入口。
- 新增 `AssistantResultsExecutionTest.kt`、`AssistantResultsUiTest.kt`；补齐旧 `FrontendAlignmentTest` 的离线商品列表响应，避免普通读取被误记为家庭管理操作。

本次未修改 App Key、用户登录令牌、服务器地址及原有30秒聊天/会话恢复读取超时。新消息继续按服务器 capabilities 选择现有新版流程，旧请求仍保留恢复入口。
