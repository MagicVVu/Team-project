## 数据与恢复机制

1. 资料状态按服务器、账号和家庭隔离，批次四分区共用一个 facts_version 与队列。首次读取服务器版本；保存正文先持久落盘，再发 PATCH。
2. 结果未知时，原 operation_id 和原正文保留，界面禁止覆盖为新请求。恢复后再次 GET 当前资料，避免将历史回执误当作最新状态。
3. 409/422 等明确拒绝后显示原因，版本冲突重新 GET；输入保留，必须用户明确核对最新版本才能再提交，不自动替换版本覆盖别人。
4. `JSONObject.NULL` 与没有提交区块严格区分；coverage 撤销不使用空数组。区块内部按后端完整替换规则组织正文。
5. 新资料、流水、AI 结果的数量保留 Decimal 字符串；比较、盘点差额与预期余量使用 BigDecimal。原有普通库存的 Double 字段保留兼容，并补充精确原文，未重构现有同步体系。
6. “询问这批”不拼接名称冒充唯一对象。先查询得到同家庭真实 task/revision，校验事实/候选确实包含目标批次，再调用 reference-messages。无法核实时停止，不伪造 source_task。
7. 业务提交后资料刷新失败明确保留“已提交”含义；不会因为刷新失败再次执行业务。正式执行成功仍由既有受校验的 operation receipt 建立。

## UI 一致性

- 使用现有 MaterialTheme、sage/cream 主题、圆角、字号层级和现有 Choice/Field/Confirm 组件，新二级页面共用 AlignmentCard。
- 不改变四栏主导航。库存仍是一屏展示；较长资料、统计与历史在二级面板滚动。
- 新文案提供中英文；名称、位置、单位、AI 原文与协议枚举不随语言改写。日期按家庭时区处理。
- 未显示“无风险＝安全”，未知风险及缺失日期不会伪装成正常、0 消费或 0 天。没有引入虚假按钮或伪造结果。
- ui-ux-pro-max 的限定 Compose 检索未命中，设计系统检索偏通用；实际采用现有项目主题与通用原生交互规范，没有照搬新配色或改变现有品牌。

## 公共接口仍未提供的部分

这些没有伪造前端实现，也没有自行新增后端 URL：

| 事项 | 当前边界 |
| --- | --- |
| 修改旧采购来源关联 | 后端 PATCH 仅支持 name/quantity/unit。当前保留原关联并解释限制，不删除重建记录冒充修改。 |
| 提交后 AI 反馈 | 没有公开 feedback 契约；不访问内部接口，也不把反馈失败当作业务失败。 |
| 全量业务事件时间线 | 当前仅有消费事件接口，不将其包装成开封、丢弃、移动和纠正的完整流水。 |
| 不经 AI 理解的纯结构化消费/开封/丢弃草稿创建 | 没有公开创建契约；当前使用公开的真实查询、可信引用与现有草稿确认流程。 |
| 自动计算补货提交 | 部署能力禁止；不开放计算建议直接 commit，不改变来源绕过限制。 |
| 图片 AI、音频上传、云 ASR/TTS、推送、WebSocket | 不属于已部署公开能力；语音入口仅使用系统识别后的文本。 |

尚未进行实体手机与真实服务器的新功能联合验收，包括其他成员并发修改、实际权限变更和付费 AI 的批次理解。离线合同与 UI 测试不能代替上述验收。可安装新 APK，使用专门测试家庭手动联验；无需修改前端配置。具体字段和授权最终由当前服务器验证。
