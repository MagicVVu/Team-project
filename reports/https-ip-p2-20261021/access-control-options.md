# P2访问限制评估（未实施）

| 方案 | 安全性 | 使用/维护 | Wi-Fi/移动数据切换 | 对App影响 |
|---|---|---|---|---|
| A. HTTPS + 既有账号认证 | 保护传输，沿用服务端会话/家庭权限；所有现有有效账号仍能访问，登录爆破需缓解 | 最方便，维护量低 | 不依赖固定IP | 正常Bearer，无额外客户端协议 |
| B. HTTPS + 出口IP白名单 + 账号认证 | 缩小可连接来源，但不是设备身份；共享出口/同NAT其他人可能同样被允许 | 每次出口变化可能要更新；无法假定手机号对应固定公网IP | 切换/重拨/基站变化可导致锁出；运营商CGNAT共享出口 | 原App协议可不变，但来源变化表现为连接/403失败 |
| C. HTTPS + 独立测试账号 + 额外入口控制 | 可避免使用日常数据；精确路径/方法、关闭注册、登录限流可减少攻击面；仍不是仅允许这一设备/账号 | 低到中维护，适合当前单手机；建议强且独立密码，只用合成测试数据 | 不需维护动态白名单；IP限流可能受CGNAT共享出口影响 | 当前Bearer可保持；新用户注册明确不可用；429需提示 |

推荐 **C的轻量方案**：现有专用测试账号 + HTTPS + 精确白名单 + 登录限流 + 自助注册不开放。
这不会在Nginx里识别或只允许“某一个账号”；其他合法既有账号仍能登录，必须明确接受该范围。
P2不创建账号、不改密码、不执行任何访问规则。

若必须严格限制到单手机，后续可另行批准mTLS客户端证书方案：私钥由Android Keystore保护，
Nginx验证客户端证书，原有Bearer仍保留；不能把私钥或共享秘密打进APK。正常服务端IP SAN/信任验证仍不可关闭。
这涉及客户端密钥管理和P4适配，不是本次P2/P3默认部署内容。
另一选择是独立可撤销设备凭据的附加Header，但需要安全配置/存储和客户端适配；静态APK秘密不能当可靠设备身份。
Nginx Basic Auth通常占用Authorization，与现有Bearer冲突，不直接叠加。

如用户选择B，未来在**443 API server**使用明确的 `allow <当前观察到的公网出口>/32; deny all;`，
保留账号认证；不要以X-Forwarded-For作为可信来源（本架构Nginx直接接公网）。
80的ACME挑战不能套手机IP白名单，否则CA多视角验证将失败。IPv4/IPv6出口都需实际确认；
不建议为避免锁出而放行整个运营商网段，且不能基于出口IP推定设备身份。

当前不实施IP白名单。来源变化可能影响每IP登录限流，但不会因未更新白名单被完全锁出；
每IP5次/分钟和全局10次/分钟（突发3）是草案参数，P3/P5需验证单手机体验和2GiB主机负载后再调整。
