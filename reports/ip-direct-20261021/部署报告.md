## 1. 实际架构与检查结论

```text
Android「Mewstow 内测」
  → 阿里云 TCP 8000 /32 来源规则
  → Ubuntu 原始目的端口来源白名单（Docker DNAT 之前）
  → 宿主机 0.0.0.0:8000 → backend 容器 :8443 TLS
  → 同一个 Python 进程内的 FastAPI app.main:app
      → PostgreSQL（原数据库容器和原数据卷）
      ↔ Agent（原容器，内部 HTTP，DeepSeek 引擎）

Agent → http://backend:8000（仅容器网络）
主机管理诊断 → http://127.0.0.1:8001 → backend:8000
```

实际后端代码入口为 `backend/server/app/main.py` 中的 `app`，不是仓库根部的 `backend/app.py`。运行环境是现有 Docker 镜像中的 Python 3.12.15、Uvicorn 0.35.0，依赖由 `backend/server/requirements.txt` 固定。没有在宿主机另建虚拟环境或安装另一套应用。

Compose 主配置为 `/srv/magicvvu/magicvvu-starter/deploy/compose.yaml`，既有环境文件为同目录 `.env`；业务密钥也可能由该服务器私有 Compose 配置注入，均未导出到仓库、App 或报告。最终审计确认 `.env` 内容未改变。

## 4. 实际启动、服务管理和端口

backend 当前容器命令：

```bash
python /app/magicvvu_direct.py
```

此脚本从 `app.main:app` 加载一次应用，用 Uvicorn API 启动两个 listener：内部 `0.0.0.0:8000` HTTP，外部 `0.0.0.0:8443` TLS（证书 `/run/magicvvu-tls/server.crt`、密钥 `/run/magicvvu-tls/server.key`）。单进程、无 reload、不信任代理头、禁用访问日志；TLS 请求直接进入 FastAPI，没有反向代理。

原业务单 HTTP 启动命令等价于 `python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1 --no-proxy-headers`；当前不要用这条单 listener 命令替代实际脚本，否则会丢失 TLS。

| 端口 | 访问范围/用途 |
|---|---|
| TCP 8000 | 公网 TLS，仅批准的 IPv4 `/32`；阿里云和主机都需放行 |
| TCP 22 | 既有 SSH 规则，未改动 |
| TCP 8001 | 仅宿主回环管理 HTTP，不在云端放行 |
| 容器 TCP 8443 | TLS listener，不单独发布该宿主端口 |
| 容器 TCP 8000 / 8767 / 5432 | 后端内部 HTTP / Agent / PostgreSQL；不公开 |
| TCP 80 / 443 | 本方案不需要新增规则 |

8000 原本由本项目回环发布使用，没有其他项目冲突，因此复用为公网 TLS。不是额外抢占一个未知服务端口。Ubuntu UFW 原本 inactive，未关闭任何防火墙；Docker 端口可能绕过 UFW，因此采用 DNAT 前的 raw PREROUTING 白名单，并以 Docker unit drop-in 确保先加载规则再启动 Docker。规则只针对原始公网 TCP 8000。

```bash
sudo systemctl status magicvvu-direct.service magicvvu-direct-firewall.service
sudo docker compose -f /srv/magicvvu/magicvvu-starter/deploy/compose.yaml ps
sudo docker logs --since 10m --tail 100 magicvvu-starter-backend-1
sudo journalctl -u magicvvu-direct.service -u magicvvu-direct-renew.service --since today
sudo systemctl reload magicvvu-direct.service                 # 只重启 backend
sudo systemctl reload magicvvu-direct-firewall.service        # 只更新来源规则
sudo systemctl list-timers magicvvu-direct-renew.timer
sudo systemctl start magicvvu-direct-renew.service            # 到期检查，未临近则不重启
```

进程异常恢复由原有 Docker `restart: unless-stopped` 执行；systemd `magicvvu-direct.service` 为 oneshot，显示 `active (exited)` 是正常状态，不是另一个 Python 后台进程。Docker 和本次 units 都已启用开机启动。不要用 `systemctl stop magicvvu-direct` 代替停止容器；如需维护停服，应在已检查的 Compose 目录使用 `docker compose stop backend`。

**不要用 restart 防火墙 unit 更新 IP**：Docker 依赖它，停止该 unit 会连带停止 Docker。本次完善依赖时实际触发过一次 Docker 重启，三个原容器随后恢复 healthy；现已提供 ExecReload，后续维护使用 reload。Docker 日志有历史 sandbox 清理和旧 security_opt 写法警告，本次未清理历史容器或改无关配置。

```bash
curl --fail http://127.0.0.1:8000/api/v1/health
```

脚本先恢复原 backend 配置为宿主回环 HTTP 8000，再移除本次 Docker 依赖、停用本次 units 和精确的自建 raw 规则；保留证书及备份，既不删除数据库卷也不删除 `.env`。随后在阿里云移除本次 TCP 8000 的公网规则。Android 改回原来的受控 SSH 诊断方案（旧隧道脚本需 `-RemoteHttpPort 8000`）；普通 debug 仍要求真正隔离的后端，不能通过伪造 `ISOLATED_APP_TEST` 复用共享业务库。

若未来已升级过镜像/Compose，先审阅恢复点，不能盲目把本报告的旧 Compose 覆盖后续合法变更。回滚脚本已做语法检查，未在当前成功部署上实际执行破坏性回滚。
