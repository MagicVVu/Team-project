记录日期  2026年10月14日    负责人  MagicVVu    阅读对象  后端开发及联调测试成员
AI 侧已完成独立 P1 服务，可解析新增、消耗、查询、用户指定采购草稿，以及开封、整批移动、丢弃和结构化澄清续接。后端接下来需要提供可信库存读取、保存任务与草稿，并在用户确认后执行事务写入。本说明以当前实际 AI 契约为准，业务接口按既有协作规划列为待实现。

完整调用路径
App 提交原文 → 业务后端认证并调用 AI → AI 通过只读工具取事实 → 返回回答、澄清或草稿 → 后端保存 → 用户补字段或核对 → 后端重新校验 → 同事务更新批次、事件、草稿与幂等结果 → App 刷新真实库存。
建议开发顺序
•  先扩展批次与事件模型，并提供两个只读接口，使用真实测试数据验证身份与返回字段。
•  再接 AI 消息网关、澄清任务保存和草稿管理，先跑通不写库存的完整链路。
•  随后实现三个动作的确认事务与撤销，最后验收并发、回滚、重启持久化和 App 展示。
重要状态：AI 开发与实测已完成；业务网关、正式数据库和页面接入仍待实现或验收。现有上传手机库存快照的过渡网关不能替代上述正式链路。
2 需要后端提供的库存只读接口
库存搜索
GET /internal/v1/inventory/search?name=牛奶响应  {"data": {"batches": [Batch]}}
name 省略时返回当前家庭库存；支持同名多批次和零库存，保留正确结束状态。AI 会优先选择精确名称匹配，并在多个候选时要求用户选择。
按批次读取
GET /internal/v1/inventory/batches/{id}响应  {"data": {"batch": Batch}}
续接时通过此接口重新读取已选批次；目标不存在或无权访问按资源不可访问规则返回 404，不能自动换成其他同名批次。成功响应必须是请求的同一 ID。
Batch 字段
格式与含义
id  household_id  name
真实批次 ID、所属家庭和物品名；与认证范围一致。
quantity  unit
数量不小于 0；Decimal JSON 建议用字符串；单位必须受支持。
location
位置字符串或 null；未知保持 null，不用虚构的默认位置。
purchased_at  label_expiry
YYYY-MM-DD 或 null，分别为购入日期与标签日期。
opened_at
新增 nullable 日期字段；不要与状态或标签有效期混合。
status
ACTIVE、FINISHED、REVERSED 或新增 DISCARDED。
version
大于等于 1 的整数；每次真实库存变更递增。

读工具认证
Authorization: Bearer <BACKEND_TOOL_TOKEN>X-User-Id: <已认证用户>X-Household-Id: <已认证家庭>
后端核验独立读 token、用户成员关系及资源归属，不能仅相信 X-Household-Id。该凭据不授予写入权限；AI 额外检查跨家庭数据、重复 ID 和按 ID 返回的一致性。
3 后端如何调用 AI 并保存结果
内部消息接口
POST /agent/messageAuthorization: Bearer <AI_SERVICE_TOKEN>X-User-Id: <已认证用户>X-Household-Id: <已认证家庭>{"text":"牛奶昨天开封了", "request_id":"request-1", "household_timezone":"Asia/Shanghai"}
此接口成功时直接返回 AgentResult，不包业务网关 envelope。HTTP 401 表示认证失败，422 表示请求字段错误；处理中的业务或模型错误也可能以 HTTP 200 加 status=error 返回，不能只按 HTTP 状态判成功。
AI status
后端处理
answered
返回只读回答与 facts；可能是查询、重复开封、原地移动或终态提示，不写事件。
needs_clarification
保存完整 clarification、候选和当前 revision，向 App 返回任务 ID 与可补字段。
needs_confirmation
保存 draft、preview、trace_id 和草稿 revision；进入编辑与用户确认，尚未写库存。
unsupported
返回能力边界与重新输入提示；不创建可执行库存变更。
error
读取 error_code、retryable；保留原文及返回的澄清字段，提示重试或手动处理。

本阶段动作草稿
{"action":"OPEN","name":"牛奶","batch_id":"milk-1", "expected_version":7,"opened_at":"2026-10-13"}{"action":"MOVE","name":"牛奶","batch_id":"milk-1", "expected_version":7,"to_location":"厨房"}{"action":"DISCARD","name":"牛奶","batch_id":"milk-1", "expected_version":7,"discard_mode":"all", "quantity":"3","unit":"盒"}
OPEN 与 MOVE 无 quantity 字段。DISCARD 的 all 数量来自当前读工具；用户编辑草稿后由后端按同一动作规则重新校验并增加草稿 revision。preview.prospective=true，只是拟议前后对照，不能作为已写入凭证。
4 澄清任务保存与结构化续接
AI 无状态。后端必须保存并按任务 ID 读取最新 context，不能把 App 提交的完整 context 直接交给 AI，否则内部自洽的旧上下文可能被重放。当前 AI 的校验无法代替任务存储。
需要保存的内容
用途
任务 ID  用户  家庭
所有读写绑定身份，App 不能指定他人家庭或任务。
原文  parsed  trace_id
保留原任务动作和已提取字段，继续处理而非重新解析原文。
candidates  selected_batch_id
保存完整候选及库存快照，供续接检查真实库存变化。
allowed_fields  revision
限制补字段并拒绝乱序；使用数据库条件更新保护并发提交。
created_at  expires_at  时区
默认有效期 15 分钟；补字段不延长有效期；相对日期参考原任务时间。

业务与内部接口分开
待实现的业务入口POST /api/v1/agent/clarifications/{id}{"revision":1,"answers":{"batch_id":"milk-1"}}后端装配后调用现有 AI 接口POST /agent/clarification{"context": <数据库保存的最新完整对象>, "revision":1,"answers":{"batch_id":"milk-1"}}
上例的 context 占位表示完整对象，实际可发送 JSON 见同目录 examples.json 的 continuation_request。AI 接口请求沿用上一页的服务认证和身份请求头。
续接结果处理
•  只允许当前缺失字段或候选 batch_id；原动作、全部模式、家庭和版本不能放进 answers 修改。
•  AI 保留已填字段并递增 context revision；再次澄清时，后端用期望旧 revision 做条件更新，保存新上下文再返回 App。error 若带更新 context，也要保留其字段与修订。
•  批次事实变化返回 VERSION_CONFLICT 和新候选，要求用户再次选择；不能把最新版本自动填入旧草稿并直接执行。
•  过期或修订冲突时，获取最新任务或重新提交原文；结构化续接不调用付费模型。确认事务仍是独立步骤。
5 确认事务 事件与撤销
用户确认后的后端事务
沿用已规划的草稿确认接口：POST /api/v1/drafts/{id}/confirm，请求携带草稿 revision 和 Idempotency-Key。以下属于后端待实现约束，本次 AI 服务不提供该写接口。
•  先核验用户、家庭、草稿状态及最新 revision，重新读取目标批次并检查 expected_version、状态、日期和数量单位。
•  在同一数据库事务内更新批次、追加事件、关闭草稿，并保存成功幂等结果；任一步失败全部回滚。
•  同一用户与家庭的同键同请求返回原结果；同键不同请求拒绝。数据库唯一约束与条件更新保证同版本并发最多一次成功。
•  提交结果不明时使用原键核对或重试，不使用新键重复执行。草稿 revision 与批次 version 是不同概念，不能混用。
动作
状态与事件语义
OPEN
写 opened_at；数量差 0；追加 Opened 并递增批次版本。已开封不重复写事件。
MOVE
更新位置；数量差 0；追加 Moved 并递增批次版本。原地移动不重复写事件。
DISCARD 部分
减去明确数量；仍有库存时保持 ACTIVE；追加 Discarded，不计消费。
DISCARD 全部
确认时重核当前数量；版本变化先重新确认；归零置 DISCARDED。
CONSUME
仅真实使用计入消耗；归零置 FINISHED，不能与丢弃混为一类。

最近变更撤销
扩展已规划的 POST /api/v1/inventory/events/{id}/undo，携带 expected_version 与幂等键。仅允许撤销该批次最新、可撤销事件；原事件保留，追加 Correction 并恢复日期、位置、数量和状态。存在后续变化时拒绝直接恢复，避免覆盖新事实。
追溯与失败记录
保存 actor、request_id、trace_id、事件时间、来源及前后快照，让一次输入能够关联到草稿和最终事件。AI 与工具失败不应写库存事件；已写入但刷新失败时保留成功结果和事件 ID，单独提示读取失败。

联调验收清单
验收场景
必须看到的结果
三个动作正常流程
开封与移动数量不变；部分丢弃减量，全部丢弃结束状态正确。
多批次与缺字段
显式选择／补字段后进入草稿；未确认不写库存；候选信息完整。
并发与重试
重复确认只执行一次；旧版本不能覆盖新库存；乱序澄清拒绝。
失败与重启
事件写失败整体回滚；重启后库存、事件、任务、草稿与幂等结果仍在。
撤销与权限
最新事件可恢复完整状态；后续变更不被覆盖；跨家庭不可读写。
App 呈现
区分草稿和已写入；冲突需重核；错误保留输入；查询与详情一致。
