## 2. 对交接文档的判断

文档明确了可用的对接架构：Android 通过业务后端认证，后端调用 AI，AI 再用独立令牌读取后端库存，PostgreSQL 保存权威数据。AI 不直接访问数据库，不保存任务，不执行确认写入。这与现有 P1/P2 的基本职责一致，可以沿用。

按文档记录，服务器完成了 FastAPI v0.6.0、AI P1 rules、PostgreSQL 17 三容器部署，数据库迁移至 `20261014_0005`；健康、数据库就绪、基本双向通信及不存在家庭的拒绝检查已通过。但当时用户、家庭、库存和 AI 任务均为零，真实用户正向问答尚未运行。健康检查和负向鉴权不能证明批次读取、澄清、草稿落库、幂等和断线恢复完整可用。

文档描述的是 P1 部署基线，没有覆盖 P2 的 QUERY_RISK、新增风险结果和扩展批次字段。本次对接应分两条连续工作：先验收 P1 与真实后端的链路，再在相同认证、任务与只读边界内接入 P2。

后端版本 `0.6.0`、AI P1 应用版本 `0.2.0`、AI P2 应用版本 `0.3.0` 和产品阶段 V1-P2 分属不同版本体系。替换 AI 不代表后端自动进入 v0.7，也不表示确认写入已经实现。

| 费用账本 | 服务器 agent_cache 是新卷，与本地历史账本不同 | 开启付费前确定共享预算与历史支出的计算方式 |

### 3.1 必须优先处理的实际问题

**引擎变量不会自动兼容。** P2 `app.py` 读取 `P2_ENGINE`，未设置时采用 `deepseek`。服务器当前将 `MAGICVVU_P1_ENGINE=rules` 映射为 `P1_ENGINE`，不能控制 P2。部署配置必须显式注入 `P2_ENGINE=rules`，并检查 `/health` 的 `release_version=V1-P2`、`engine=rules`、`inventory_writes=false`；不能只看健康 HTTP 200。

**后端风险响应兼容性尚无源码证据。** P2 `AgentResult` 增加 QUERY_RISK、risks、evaluated_count，facts 是扩展 Batch。若后端使用严格 P1 模型校验，可能拒绝这些字段；若重建精简响应，也可能丢失它们。必须检查 `agent_gateway.py`、schemas、任务/草稿 JSON 存储和 GET 读取路径，完成保存前后字段一致性测试，不能只测试 reply 文本可见。

**旧 P1 不接受直接新增的批次字段。** 共用基础模型配置 `extra=forbid`，原 P1 Batch 会拒绝 P2 扩展字段。不能先让库存接口无条件输出新字段，再继续运行 P1。推荐先上线兼容旧批次的 P2，再用可关闭的后端字段输出配置启用扩展；回滚 P1 前先关闭扩展输出。若必须长期并行运行 P1/P2，应先定义版本化工具响应或能力协商，保留 P1 投影，不能依赖忽略未知字段。

**风险澄清尚未闭环。** P2 Manager 对“这批/这盒/这个”且无名称的输入返回 `needs_clarification`、`missing_fields=[name]`，但没有生成 clarification context；当前 `/agent/clarification` 仍只接受 P1 上下文。通用表单不能假设该结果可按已有 task 续接。

推荐为风险选择建立版本化 P2 上下文，仅允许补充名称或选择已核实的候选批次，沿用服务端作用域、revision、有效期和重新读取机制；续接直接评估，不调用模型。风险资料缺失另由业务编辑功能补全，不能通过答案修改真实事实。此方案需与后端的上下文校验联合冻结。若首轮只能先接入现有能力，应明确限制这类输入并引导发送完整新消息，不能宣称已支持风险澄清续接。

### 3.2 数据字段映射

基础映射沿用文档，但以 v0.6 实际 serializer 为准：

| 数据库字段 | AI 字段 | 要求 |
|---|---|---|
| storage_location | location | 可空；位置名称不代表实际温度 |
| expires_on | label_expiry | YYYY-MM-DD；本身不说明日期类型 |
| purchased_on | purchased_at | YYYY-MM-DD 或 null |
| quantity NUMERIC(16,6) | quantity | 十进制字符串，不转换为浮点数 |
| opened_at/status/version | 同名 | 保留真实日期、四种状态和版本 |

P2 的七个扩展字段需要可追溯业务来源，是否放在批次表、商品元数据表或经关联读取，应核对真实模型后决定：

| 字段 | 允许值/未知值 | 不能采用的默认推断 |
|---|---|---|
| category | food/medicine/household/unknown | 根据名字自动确认为食品或药品 |
| product_id | 字符串或 null | 用名字代替经过管理的商品 ID |
| label_date_type | use_by/best_before/expiry/unknown | 将所有 expires_on 视为安全期限 |
| label_context_valid | true/false/null | 认为烹饪、冷冻、分装后原标签始终适用 |
| storage_condition | ambient/refrigerated/frozen/null | 将“冰箱上层”等位置自动当作已核实冷藏条件 |
| label_storage_condition | 同上 | 为标签补造保存要求 |
| is_opened | true/false/null | 将 opened_at=null 当作未开封 |

P2 可以读取只有 P1 字段的旧记录，但风险字段未知时将返回待核对，不能据此生成完整期限判断。部分明确严重风险可以保留，但最终结果取决于实际登记事实和规则适用性。

历史单位“件”不能无条件替换为“个”。需由业务维护规范单位与可靠映射；无法确认时明确拒绝或要求人工修正。搜索超过 1000 条不能截断，应报告范围限制；分页或更大数据量另行设计。

## 4. 推荐接口与部署方案

第一轮继续使用现有业务消息入口：

`Android → /api/v1/agent/messages → P2 /agent/message → 后端库存只读工具 → PostgreSQL`。

风险查询返回 answered + risks；库存动作仍产生 P1 语义的草稿。后端持久化完整版本化结果，App 只接收允许公开的字段，服务器保存的原始澄清 context 不下发 App。

P2 已有 `/risk/evaluate` 和 `/knowledge/rules`，两者继续属于内部服务能力。若后续物品详情需要直接评估，再由业务后端添加经过用户/家庭鉴权的代理路由并提供正式 OpenAPI，不能让 Android 持服务令牌直连 AI。首轮聊天联调不依赖新增这个对外路由。

`reminder_days` 是 P2 请求新增项，默认 3、范围 0–365。初期可以由后端固定使用默认值；若开放配置，必须加入消息 schema、转发和幂等指纹。同一 request_id 下文本、家庭、时区或提醒窗口改变，应判为不同请求；最终指纹以实际 v0.6 实现核对。

家庭时区虽由 App 字段传入，仍需后端校验并统一可信来源；后续有家庭设置时应使用服务端设置。AI 评估时间来自受信任服务时钟，不接受客户端上传“当前时间”以修改风险结论。

部署继续保留服务名 `agent` 与容器内端口 8767。本地示例 8768 不构成服务器端口要求。拟使用工厂入口 `p2.app:create_app`，显式 rules，引入 p2 模块及 rules.json，并保留 p0/p1、所需运行依赖及 eval/pricing.json；具体 COPY、WORKDIR、启动命令、探针和卷挂载待取得真实 Dockerfile/Compose 后修改。

P2 自带规则文件应包含在只读镜像内；管理员规则路径可只读挂载。费用账本实际位置由源码定位为 agent 根目录下 `.cache/p0/budget.sqlite`，需核实该位置在服务器可写持久化卷内，而非只读根文件系统。不得清空数据库卷或复制覆盖运行中的 SQLite 账本。

AI 总处理截止时间维持 10 秒；工具单次 HTTP 超时现为 5 秒。后端读取 AI 超时应略大于 AI 截止时间，例如 12–15 秒，并与代理、处理租约共同核对。文档中的 30 秒租约不是超时后可无限重发的许可：进程中断、租约到期但上游是否调用未知时，必须明确恢复策略，防重复付费。新 request_id 不应用作超时的自动重试方式。

## 6. 联调测试清单

使用真实 PostgreSQL 和真实服务 HTTP。单元测试仍可使用测试夹具和进程内替身，但不交付运行用假库存服务或演示页面。先用独立测试环境；如果只能在当前服务器测试，由后端准备专属测试用户/家庭，记录所有创建 ID、限定清理范围，不开启全局未验证注册，不删除数据卷或清空业务表。

| 场景 | 必须验证的行为 |
|---|---|
| 单批次库存问答 | 数量、单位、位置、日期、状态、版本与 PostgreSQL 一致 |
| 同名多批次 | 返回完整候选，不默认选择第一批 |
| 开封、移动、丢弃 | 草稿/前后预览正确，库存保持不变 |
| 重复开封、原地移动 | 返回已有事实或无需变更，不生成重复操作 |
| 缺字段及多轮补充 | 后端保存最新 context、revision、TTL；结构化续接不调用模型 |
| 风险指代缺名称 | 按冻结的 P2 契约恢复，不出现无法续接的伪澄清状态 |
| 过期、旧 revision、库存变化 | 拒绝或重新核对；不让客户端覆盖版本/动作/身份 |
| 同键同内容及并发 | 只启动一次 AI 处理，最多一份草稿；恢复后仍有效 |
| 同键不同输入 | 包含时区/提醒参数的指纹一致性检查，冲突拒绝 |
| 跨家庭、另一用户任务、成员退出 | 内部读取和任务读取重新鉴权，不泄露事实或 context |
| 精度、非法单位及超上限数量 | 不用浮点数改值、不擅自映射“件”、不截断批次 |
| P1旧批次输入P2 | 可读取；缺风险字段明确 unknown，不捏造类别/温度/标签 |
| 日期含义、标签适用性 | 品质日期与安全期限区分，适用性未知不强推结论 |
| 实际保存条件与标签要求不一致 | 按真实记录输出证据和关注，不从位置推断 |
| 终态/零库存 | excluded 正确，不作为当前可用库存关注项 |
| 已开封但无商品规则 | 提示缺商品专属规则，不使用通用品类天数 |
| 风险结果保存和GET恢复 | risks、facts、evaluated_count、规则版本、证据不被丢弃 |
| 工具故障、模型格式错误、总超时 | 保留可恢复信息；不产生可确认错误草稿，不自动付费重试 |
| 处理中重启或租约到期 | 任务恢复策略明确，重复调用风险有记录和约束 |
| 提示注入 | 无法更改作用域、规则、工具地址或强制写库存 |
| P2扩展开关与回滚P1 | 关闭扩展后 P1 仍能解析，数据库数据不丢失 |
| 所有AI路径 | 可以写任务/草稿；库存、购物清单业务数据不因 AI 调用变化 |

测试记录保存请求标识、trace_id、task_id、draft_id、实际版本、前后事实和断言；不保存明文 token、密码、手机号、完整私密配置或未经脱敏日志。P95 统计需说明样本数、并发、rules/模型模式、AI 内部耗时及端到端耗时，不能用本地模型 1.908 秒替代服务器结果。

## 7. 模型、规则与预算门槛

当前应保持 rules 联调。真实模型保留集存在 1 条拒绝输出（59/60），修复后应使用新增独立保留样本验证，并保留原失败记录；不得通过反复调参同一保留集宣布完全通过。模型格式失败必须继续安全降级。

规则仅完成自动来源核对，不是人工专业审核；当前生产规则没有商品专属开封天数。即使数据接齐，也不能宣称可以对所有商品做开封期限判断。补充真实商品规则需要商品标识、包装要求、来源及审核记录。green 不等于安全，safety_guaranteed=false 必须在契约中保留。

本地历史费用记录截至 2026-10-14 为估算累计 0.589254 元，团队管理上限 20 元；这不是供应商账户的实时余额。服务器新缓存卷不能自动继承本地支出。开启付费前需核对最新本地账本、服务器账本、供应商实际计费和团队其他调用，确定一个权威预算口径；迁移或额度调整必须明确支持方式，不能让多个环境各自重新获得 20 元。继续保留价格有效期校验、调用前预算预留和无自动付费重试。
