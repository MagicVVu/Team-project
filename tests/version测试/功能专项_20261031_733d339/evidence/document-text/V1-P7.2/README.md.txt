## 保留的失败与修正

1. 首次独立恢复在 PostgreSQL 初始化的临时服务阶段过早判定就绪，恢复未通过，自动恢复旧应用配置，未开始生产迁移。改为等待最终 TCP 服务就绪后，用新的独立备份及恢复实例重新验证，通过后才迁移。原失败和私有日志保留。
2. 第一次新版本的配置、数据库和 P7 预检通过，但实际模型调用返回 `MODEL_UNAVAILABLE`，流程自动回退到旧应用，保留 0007 审计表，没有 downgrade 或删除表。
3. 进一步实测发现主机当前两个 DNS 上游超时；直接查询 `223.5.5.5`、`223.6.6.6` 可解析 DeepSeek。使用不带密钥的临时容器在生产 AI 网络验证 DNS/TLS 后，只给生产 AI 配置这两个解析器及 `dns_search: ['.']`。没有修改主机 DNS、VPN、Docker daemon 或其他服务。
4. 修复后重新切换并做一次模型验证成功。失败请求的保守预算预留保持未知用量，没有当作零费用删除；没有同条件自动付费重试。

两套临时恢复容器及其副本卷在验证完成后，按固定名称、所属标签、停止状态及非生产卷检查后清理。私有备份 dump、旧镜像和失败证据保留。
