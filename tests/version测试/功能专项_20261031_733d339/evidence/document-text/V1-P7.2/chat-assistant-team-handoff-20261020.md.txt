## 2. 通用边界：继续保留的实现

1. 数据库任务网关适合当前项目，继续保留；新引用适配器、规划读取和业务动作在独立模块承接，不整体替换网关。
2. Android 仅持有用户会话，不直连 AI 内网或数据库，不持有 DeepSeek／内部服务密钥。
3. AI 识别任务、判断缺失字段、生成草稿；库存计算、单位换算、日期解析、权限、版本与提交由确定性代码处理。
4. 单物品、单动作。开封再移动、多个物品联合处理要求分次提交，不扩大为批量执行。
5. AI 的五种结果为 `needs_clarification/needs_confirmation/answered/unsupported/error`；`processing` 是网关任务状态。业务执行状态单独查询。
6. 点击确认、收到草稿、回复文字说“完成”，均不是已执行凭证。只有正式回执能建立成功状态。
7. 现有确认、取消、回执恢复及稳定 operation_id 机制继续复用。修改后仍需覆盖并发、重试与进程重建。
8. 不新增 Mock、演示页面、长期记忆、多 Agent、自动下单；Jev 继续暂缓。

## 3. T01：先解决安装包与正式服务连接

### 当前情况

- `frontend/app/build.gradle.kts` 的 Debug 默认地址为 `http://10.0.2.2:18080`，这是模拟器访问宿主机的地址，并非手机公网地址。
- Release 的 `mewstowReleaseApiUrl` 默认空，未配置时网络功能保持关闭。
- `TargetPolicy.health()` 要求 `isolated_test == BuildConfig.DEBUG`：Debug 只接隔离服务，Release 只接正式服务。
- `CloudApi` 在登录及其他 POST 前也做环境校验。因此只把 Debug 地址换为公网域名，仍会被正式服务的 `isolated_test=false` 拒绝。
- 仓库中已有本地 Debug APK，不证明用户手机安装的是该包；接手者必须记录实际安装包来源。

### 前端要做什么

1. 选择既有 Release 路径，按发布流程构建一个连接正式 HTTPS 的受控候选包；不要为了测试去删除环境隔离判断。
2. 构建参数示例：

   ```powershell
   .\gradlew.bat :app:assembleRelease -PmewstowReleaseApiUrl=https://iz7xvftxzwe1mwbso1ovyyz.tail0abb88.ts.net
   ```

   在 `frontend` 目录执行。该命令不自动完成正式签名或分发；签名走项目已有受保护流程，不把密码放入仓库或命令记录。
3. Base URL 只填 HTTPS 根地址，不附加 `/api/v1`，不写公共 IP 常量，不关闭证书与主机名校验。
4. 核对最终包的 DEBUG 标志、CLOUD_API_URL、清单和签名。若后端未来改服务版本，双方同步更新兼容策略；不放宽为接受任意版本。
5. 登录并选定家庭后，必须进入 CloudAssistant；游客模式的本地规则回答不能作为 DeepSeek 接通证据。
6. 调试包继续连隔离服务。若团队需要独立预发布构建类型，另行设计环境标识与兼容测试，不将其混为当前已经存在的配置。

### 后端／部署要做什么

- 确认 HTTPS 健康、数据库 ready、版本及环境标识、用户登录、家庭权限和执行能力声明一致。
- 提供受控联调账号／家庭，不要求前端持有内部服务令牌。
- 对照根目录公网报告复核 DNS 持久性、登录防滥用、公开文档与内部路径暴露的处理状态；公网访问成功不代替发布验收。

### 验收

同一最终 APK 依次完成健康检查、登录、家庭选择、查询库存、恢复原任务。用移动网络检查，记录 APK 摘要／构建号／签名、地址、时间及后端版本。Debug 连接正式服务继续被拒绝。

## 4. T02：自然语言补充必须续接原任务

### 当前情况

前端已经能点击候选和提交结构化字段；主聊天框只特殊识别“第一个／第二个／第三个”，其余文本通常新建任务。表单多个字段共用一个输入值，切换字段会丢失前一字段的待填值。

AI 提供 `agent/conversation/replies.py` 的 `resolve_reply()` 行为参考：可确定性解析候选序号、明确数量／单位及日期；它不是现成 Kotlin，也不是已开放的 HTTP 路由。

### 前端要做什么

- 显式保存当前活动任务 ID、修订、允许补充字段、该修订候选顺序及有效期；不能只认聊天列表最后一张卡。
- 把每个字段的值独立保存为字段映射。一次可提交多个允许字段；请求结果未知后封存原请求体，不能覆盖待核实的澄清。
- 主输入框在存在有效待澄清任务时，优先做确定性续接解析：

  | 输入 | 处理 |
  |---|---|
  | 第二个、选择第二批、选择第二个吧 | 解析当前修订的候选序号，提交对应真实 batch_id；不得默认第一批 |
  | 两盒、2 盒 | 只有 quantity/unit 都允许补充时提交相应字段；只缺数量时可按已知单位规则处理，含糊则用表单 |
  | 今天、昨天、YYYY-MM-DD | 只有一个明确允许日期字段时续接；多个日期字段时询问具体补哪一个 |
  | 这一批 | 只在当前任务已明确选中真实批次且该字段允许补充时承接 |
  | 开始新任务、明确提出另一个物品／动作 | 退出旧续接分支，清除活动对象引用；旧任务保留，可单独恢复 |
  | 无法唯一判断 | 保留输入，展示具体字段／候选，不让模型猜测 |

- 有效续接调用原 `POST /api/v1/agent/clarifications/{task_id}`，不新建 message；不要把普通澄清当作草稿编辑。
- 日期转换使用家庭时区与可信时间；手机设备日期不作为最终权威。明确日期表单可要求 YYYY-MM-DD，聊天中的相对日期由受信流程解析。
- 候选补齐开封日期、状态、数量单位、位置、购买／标签日期和版本；序号必须绑定修订，旧列表不可套到新列表。

### 后端要做什么

- 继续使用原有任务归属、最新 revision、有效期、allowed_fields 和候选校验；澄清后重新读取库存。前端解析不替代后端验证。
- 保持九字段 answers：`name/quantity/unit/location/purchased_at/label_expiry/opened_at/to_location/batch_id`。不能经答案修改 action、家庭或 expected_version，也不加 item_key 绕过公开协议。
- 修订冲突返回明确错误，客户端 GET 最新任务后重新核对。库存变化时重新展示，不自动替换版本后执行。
- 当前网关仅允许 needs_clarification 续接；error、过期或已完成任务不伪装成原任务继续。保留原文和已填字段，允许用户明确选择重新处理。
- 若团队选择把文字解析放后端，作为独立确定性调用适配层承接并沿用现有澄清流程；先写明新契约再实现，不假定已有文字续接接口。

### 验收

多于三个候选仍可选择；“选择第二批”进入原 task_id；缺数量时“2盒”、只缺开封日期时“昨天”进入原任务；同时缺两个日期时继续询问。结构化续接模型调用数为 0；非法字段、旧修订和跨家庭选择被拒绝。

## 5. T03：查询后继续问“它在什么地方”

### 当前情况

- AI 支持版本化 `p7-object-reference-1`，引用最长 15 分钟；每次重读真实批次，不继承历史数量、位置或版本。
- 前端目前拦截部分“它”的表达，没有完整引用状态。
- 后端 `POST /api/v1/agent/reference-messages` 已预留 DTO，但实现仍固定返回 503。不能仅修改能力布尔值宣称接通。

### 后端要做什么：完成独立受信适配层

公开预留请求字段如下；仍需补实现、持久化绑定与测试：

```json
{
  "household_id": "<当前家庭 UUID>",
  "text": "它在什么地方？",
  "request_id": "<稳定请求 ID>",
  "household_timezone": "Asia/Shanghai",
  "source_task_id": "<来源任务 UUID>",
  "source_revision": 2,
  "batch_id": "<来源结果中的真实批次 UUID>"
}
```

这些占位值是协议说明，不是测试库存，也不是可直接发送的完整数据。

1. 根据当前登录身份和家庭成员关系，读取来源任务，校验归属、最新修订和可引用状态。
2. batch_id 只能来自该修订的真实 facts／candidates／允许的变更前事实；多个对象必须有用户明确选择。名称相同不意味着对象唯一。
3. 明确“最近选择”的批次以及首次建立引用的时间和截止时间；由后端核实／记录。不能把手机给出的 source_task_id 当作自动可信证明。
4. 刷新窗口、GET 恢复、同键重放不能重新签发并延长旧引用。过期后需重新查询或明确选择，再建立新的有效绑定。
5. 构造内部 `ObjectReference`：`protocol_version/scope/source_task_id/source_revision/batch_id/issued_at/expires_at`。scope、时间由后端生成，不接收手机历史数量或库存版本。
6. 将原文和引用分别传给 AI 内部 `/agent/message`。不要拼成“牛奶在什么地方”冒充用户原文；保留原 text、request_id 和证据链。
7. 幂等绑定须包含原文、时区和完整引用身份：同 ID 同体返回原任务，同 ID 换来源／修订／批次拒绝。复用现有任务持久化、租约和恢复机制，不引入另一套任务网关。
8. 私有续接上下文仍由后端保存；公开响应沿用任务外壳。补字段继续使用原澄清接口，GET 恢复不调用模型。
9. 批次删除、终态、成员资格变化或来源修订变化时返回明确原因，要求重选；不得回退成第一批或相同名称的另一批。
10. 实现并验证后才把 `trusted_reference_messages` 改为 true。不更改普通消息四字段契约。

### 前端要做什么

- 只有一个真实批次的查询结果可建立当前对象；多个结果展示选择，不能默认第一条，也不跨家庭共用。
- 保存来源任务／修订、明确选择的批次和后端认可的截止时间。恢复时重新核对，不能用本地缓存续期。
- 有有效引用时调用独立 reference-messages；没有引用时提示补名称或选批次，不再全局按字符串拦截“它”。
- “开始新任务”、明确新对象、切换家庭、退出账号清除活动引用；历史任务与正式回执继续保留，旧异步回复不得写入新家庭。
- 展示“当前指向哪一批”的可见提示和重新选择入口。不要仅靠隐藏的最近聊天文字推断对象。

### 验收与 AI 兼容注意

唯一查询对象 → “它在什么地方” → 返回重新读取的位置；期间另一成员移动物品，要回答新位置。多对象、过期、删除、终态、跨家庭与旧修订必须重新核对。

现有 AI 零模型字面模板明确覆盖“在哪里／在哪／在哪儿／的位置／放在哪里”等表达，不能把“它在什么地方”当作已实测通过。该原句必须纳入联调；若走模型或需补同义表达，由 AI 维护者核对预期。前端不得偷偷替换用户原文，不能承诺所有同义问法都零次模型调用。

## 6. T04：开封（OPEN）

### 当前情况

AI 命令为 `action/name/batch_id/expected_version/opened_at`，无需数量，重复开封会返回已有事实。后端执行 DTO、EDITABLE 和能力声明尚未支持 OPEN，Android 执行校验表也没有 OPEN。

### 后端要做什么

- 在既有独立确认层扩展 OPEN，复用任务／草稿／操作绑定、事务锁、版本校验和幂等回执，不新增另一套确认入口。
- 仅允许活动真实批次；日期需合法，不晚于可信家庭今天。由可信任务时区处理相对日期，不用手机时间猜测。
- 数量、单位、位置保持不变，记录开封事实与版本变化，事件建议映射为 `Opened`，与 AI 事件契约对齐。
- 同 operation_id 同体重放返回原回执；另一请求发现已经开封时返回已有事实／明确无变更结果，不覆盖日期、不生成第二次开封变更。具体返回形状需写入 OpenAPI，并与前端约定。
- 所有库存读取路径返回 opened_at；公开 DTO、批次工具与详情页字段映射一致。
- 事务能力和回执验证完成后开放 `actions.OPEN=true`，返回正确 editable_fields。

### 前端要做什么

- 在 AgentExecutionPolicy、动作表单和回执展示补 OPEN；只编辑 opened_at，不要求数量。
- 展示目标批次、原版本、开封前后日期，明确数量不变。已开封显示已有日期，不暗示再次提交。
- 能力未开放时保留草稿和明确不可用原因；若详情页也不支持开封，不用通用编辑假装完成。

### 验收

合法日期开封；缺日期→补充“昨天”；未来／非法日期拒绝；已开封不重复变更；库存版本变化先冲突。回执恢复后事件仅一条、数量和位置不变。

## 7. T05：部分／全部丢弃（DISCARD）

### 当前情况

AI 草稿包含 `discard_mode=partial|all`，以及 `name/batch_id/expected_version/quantity/unit`。all 的数量来自生成草稿时的当前批次，是待确认依据，不是提交时可以绕过版本检查的授权。后端当前 DELETE、普通数量调整均不能代替该语义。

### 后端要做什么

- 在现有确认层补 DISCARD 字段校验、执行、事件和回执，明确模式与可编辑字段。模式调整属于草稿编辑／重新核对流程，不能塞进九字段澄清接口。
- partial：要求正数、兼容单位和精确换算，不能超过当前量；剩余为正保持 ACTIVE，扣至零的丢弃终态需与 all 一致约定。
- all：加锁后检查 expected_version，再读取当前整批数量；若相对草稿发生变化，先冲突并重新生成／确认，不能静默扩大丢弃数量。
- 全部丢弃后数量为零并映射为 DISCARDED；保留原记录与审计事件，不硬删除历史、不伪装 FINISHED 消费。
- 事件映射为 Discarded，绝不记为 Consumed。终态批次不重复扣量；同键恢复返回原回执。
- 同步详情、库存工具、规划快照中的状态与数量；事件、版本、操作回执必须与库存变更处于同一事务。
- 通过专项验收后开放 `actions.DISCARD=true`。未知单位继续明确拒绝，不能放宽为任意字符串。

### 前端要做什么

- 提供“丢弃指定数量／丢弃本批全部”两种明确选项；partial 显示数量和单位，all 显示整批数量来源，不要求用户手填全部量。
- 模式或字段修改后刷新待确认摘要；需要重建草稿／修订时按后端契约操作，不修改 action、batch_id、expected_version。
- 显示原量、丢弃量、预计剩余及状态；全部丢弃有明确确认提示。操作完成只认回执。
- 支持取消和结果未知恢复；没有正式丢弃能力时不能引导删除记录来冒充。

### 验收

10 个丢弃 3 个→剩 7 个；全部丢弃→0／DISCARDED；超量、单位不兼容、精度超限、已终态均正确拒绝或返回事实。并发增加库存后旧 all 草稿不得直接丢弃新增部分；统计消费量不因丢弃增加。

## 8. T06：消费统计——先补可信事实，复用 AI 算法

### 当前情况

CONSUME 已可正式执行并写入 Consumed 事件。已有公开 `GET /api/v1/households/{household_id}/consumption-events` 是事件列表，返回 `planning_history_complete=false`；它不包含完整覆盖、稳定商品聚合等全部规划事实，不能直接将该布尔值改成 true。

AI 已有净额消费统计，处理事件去重、撤销／纠正关联、发生与录入时间、完整观察窗口；不分析展示用 history 文本。

### 后端要做什么

实现既有预留只读接口 `GET /internal/v1/planning/context`，内部服务认证并核对可信用户／家庭；响应使用 `{"data": <PlanningSnapshot>}`。可按 name 或 item_key 查询，二者不能同时传；不另造同义规划协议。

| 字段组 | 必须具备的业务含义 |
|---|---|
| protocol_version、scope | 推荐 v1-planning-context-1；真实用户／家庭隔离 |
| snapshot_id、as_of | 稳定快照标识、带时区的读取截止时间，不拼装互相矛盾的数据 |
| event_watermark、shopping_version | 可用于重验的真实事件水位及家庭共享清单版本 |
| items_complete、history_complete、pending_complete、next_cursor | 分别说明读取范围完整性，未读完不得声称完整；当前 AI 不自动把分页缺项当零 |
| item_key、item.version、name/unit/category | 稳定商品映射和版本；名称相同不自动合并，跨批次关系由业务明确 |
| batches | 真实批次、数量单位、日期、状态和版本 |
| events | id/item_key/kind/quantity/unit/occurred_at/recorded_at/committed/related_event_id |
| coverage、recording_completeness_source | 每天是否记录完整、是否断货／有未解释调整，以及可解释的业务完整性来源 |
| preferences、pending | 明确采购偏好和共享待购；统计路径也须满足现有快照必填契约，未知事实不能伪装为已知零 |
| stock_verification、usable_quantity_verified | 真实库存核对时间／来源及可用数量核验；缺失时按事实表达 |

- 事件聚合应保留必要的撤销／纠正及其原始事件，不能只按发生日期截断导致关联缺失；只采用截止时已知事实。
- 区分 Added、Consumed、Discarded、Adjusted、Reversed、Corrected 等语义，定义数据库事件到 AI kind 的显式映射。现有事件模型如缺字段，业务迁移由后端负责。
- “历史已全部取回”和“用户每天实际都完整登记”是两件事。API 读取成功不能证明记录日完整；没有核实机制时返回不足，而非补齐假的覆盖日。
- 不用批次数量差反推消费，不把丢弃、采购草稿、开封、移动计入消费。
- AI 读取快照要求 as_of 不未来、距当前不超过 300 秒；更具体容差与机器 schema 以现有校验为准。超范围／不完整读取明确返回不可用。

### 前端要做什么

展示 consumption_summary 的时间窗口、observed_days、effective_quantity/unit、状态、排除说明及原因。保留结构化字段，不能只存 reply；没有有效数据时显示记录不足，不显示“本周消费 0”。

### 验收

新增、移动、开封不计消费；丢弃排除；同事件不重复累计；撤销／纠正净额正确；跨家庭隔离；时区日界正确；缺记录日和分页未完成明确不足。

## 9. T07：耗尽预测——只给有条件的估计

### 后端要做什么

复用 T06 快照。补充实际库存核对记录 `stock_verification.checked_at/source`，与 `usable_quantity_verified` 保持业务含义一致。查询时间、API 更新时间、数据库 updated_at 不自动等于用户刚核对实物。

当前 AI 策略要求最近连续完整观察日、至少 14 天、至少 5 条有效消费事件且分布于至少 3 个日期；同时检查历史完整性、事件冲突、单位、库存等。库存核对最大年龄默认 168 小时。这些是当前项目策略，不是后端擅自变更的阈值，也不是经过真实家庭回测的准确率保证。

历史条件不足时仍可返回可核实统计，但不给未来耗尽日期。不能为了让页面出现预测而伪造覆盖日、库存核对时间或消费事件。

### 前端要做什么

- estimated：展示当前登记库存、观察窗口、参考日均消耗、剩余天数、参考日期与条件。
- insufficient_data／needs_review：显示具体欠项与补录入口，不画确定日期或倒计时。
- no_recorded_consumption：说明窗口内无有效登记消费，不显示“永远用不完”。current_zero 表示登记库存为零。
- 显示 evaluated_at／快照时间和“未来不补货、消耗水平接近观察窗口”等假设；不把参考日期包装为保证。

### 验收

充分数据可估计；少于 14 天、事件少／日期少、核对陈旧、未来核对时间、断货／未解释调整正确降级；跨单位精确换算，数据改变后重读，不沿用旧聊天数字。

## 10. T08：自动补货建议与确认加入待购

“自动”仅指根据事实计算建议或生成待确认草稿。V1 不自动提交采购、不自动支付或下单；一次只处理一个明确商品。

### 当前情况

AI 已根据最低库存或完整登记消耗＋明确采购周期计算缺口，并抵扣已确认共享待购；可输出 PLAN_ADD 与 planning_basis。后端目前仅执行用户明确数量的手动采购草稿。

后端的 automated_plan() 会拒绝自动规划；前端 AssistantStore.acceptExecution() 也会把含 planning_basis／planning_calculation／SUGGEST_PURCHASE 的待确认任务判为不可执行。双方都需要完成承接，不是只改一个开关。

### 后端要做什么

1. 在 T06 快照提供明确的 minimum_stock、coverage_days、lead_days、偏好版本；若有采购包装，order_unit 与 pack_size 成对提供，禁止猜测每盒容量。
2. 完整读取家庭共享待购，明确 pending/purchased/draft 和 confirmed；仅按契约抵扣已确认且仍待购的条目，已购买／草稿不重复抵扣。无法明确映射的商品标记需核对。
3. 聚合稳定的商品、批次、偏好和清单版本。数据缺失或可用库存未核验时，返回原因，不能用建议驱动隐式报废／扣除风险库存。
4. 自动建议草稿确认前，加载服务器保存的 planning_basis，重读并校验 item_version、batch_versions、shopping_version、event_watermark、preference_version、snapshot_id/as_of 和计算依据。
5. 库存、待购、偏好或事件变化时重新计算并要求核对；不以旧数量直接创建，也不信任手机提交的计算依据。
6. 明确“用户改建议数量／单位”的处理契约：原建议与修改后的业务输入分别审计，必要时生成新修订重新确认。AI 当前 planning_basis.human_modified 固定 false，不能在手机上篡改它伪装为模型原建议。
7. 复用现有 PLAN_ADD 事务与稳定创建标识；同操作重试只创建一项待购，加入成功回执不声称已经购买入库。
8. 在读取和确认重验均完成后开放 automatic_planning_commit，并同步 manual_plan_only 等能力含义。单独提供建议读取与允许确认执行是不同阶段，分别记录。

### 前端要做什么

- 分别展示“按明确最低库存补货”和“按登记消费／采购周期建议”，不能显示一种依据却执行另一种算法。
- 展示当前库存、已确认待购、目标库存、建议新增量、单位、原因、更新时间及缺失数据。
- 依据业务能力与具体草稿执行状态决定按钮；删除前端对所有自动规划的一刀切拦截前，先完成后端重验和回执测试。不能仅看到 PLAN_ADD=true 就开放自动规划。
- 用户点选一项生成／核对单项草稿，仍需明确确认；数据不足不提供虚假数量。建议模式没有 draft_id 时不能拿文字数量直接提交。
- 保留完整 planning_basis 供展示与任务关联；权威依据由后端加载，手机不得编辑版本、水位、原计算和受保护字段。
- 显示“已加入待购清单”，保留提交响应丢失后的原请求恢复；不显示已采购／已入库。

### 验收

最低库存路径和历史消耗路径依据正确；已有待购抵扣；包装单位明确换算；药品自动补货排除；风险／可用库存不足时需核对；另一成员新增待购后旧建议要求重验；重复点击／超时恢复只新增一项。

## 11. 共用接口与字段约定

### 11.1 继续复用的公开接口

| 方法与路径 | 用途与约束 |
|---|---|
| GET /api/v1/health | 服务版本和环境；不证明 AI 或最终页面已验收 |
| GET /api/v1/agent/execution-capabilities | 后端动作、自动规划和引用能力；按真实支持开放 |
| POST /api/v1/agent/messages | household_id/text/request_id/household_timezone，普通消息四字段不变 |
| POST /api/v1/agent/clarifications/{task_id} | revision＋非空 answers，限当前允许的九字段 |
| GET /api/v1/agent/tasks/{task_id} | 恢复任务，不重新调用模型 |
| GET /api/v1/drafts/{draft_id} | 草稿、修订和生成时的预览 |
| GET /api/v1/drafts/{draft_id}/execution | 权威执行状态、可编辑字段、原因及回执 |
| POST /api/v1/drafts/{draft_id}/commit | operation_id/task_revision/draft_revision/edits；用户明确确认后调用 |
| POST /api/v1/drafts/{draft_id}/cancel | 取消草稿，不等于撤销已执行库存操作 |
| GET /api/v1/operations/{operation_id} | 恢复正式结果；404 不能单独证明原提交没有执行 |
| POST /api/v1/agent/reference-messages | 已预留、待实现的独立引用适配入口，不是当前可用能力 |

新增动作优先扩展现有 execution/commit、业务 DTO 和回执；不要假定存在 `/confirm`，也不另建重复确认接口。后端修改 DTO 后同步 OpenAPI、能力声明、前端白名单和协议兼容测试。

### 11.2 内部只读接口

- `/internal/v1/planning/context`：待后端实现，遵循既有 V1 快照 schema。
- `/internal/v1/operations/{operation_id}`：已实现的内部凭证读取，不重复建设。当前对无批次版本的采购操作会明确不适用，不用伪造批次版本满足 AI 反馈。
- AI 只通过受认证工具读取；内部地址和密钥不进入 APK。公开消费列表不是内部规划快照的直接替代品。

### 11.3 单位、精度和保护字段

- 库存数量最多六位小数；采购最多三位小数；位置最多 100 字。超限提示修订，不静默舍入或截断。
- 吨／kg／g 和 L／ml 按同维度精确换算；台仅同单位使用，不能猜台与个、盒与瓶的换算。
- action、batch_id、expected_version、身份、来源任务和规划依据不是普通表单可改字段。改变动作或目标必须重新生成／核对。
- “全部丢弃”的模式是草稿动作参数，不能在澄清 answers 增加 discard_mode 绕过公开九字段边界。
- 候选 facts 是读取时事实；草稿 preview 是生成时预览；receipt 才是提交结果。页面明确标示来源与时间。

## 12. 状态、超时与恢复：所有新动作一起遵守

| 情况 | 页面行为 | 后端要求 |
|---|---|---|
| 正在理解／读取 | 展示处理中，可收起窗口 | AI 单次处理与澄清各保留 10 秒总截止，不自动付费重试 |
| 需要补充 | 保留字段、候选和修订 | 最新任务校验，结构化续接不调用模型 |
| 待确认 | 展示可编辑草稿和未执行提示 | 按能力、版本、有效期判断可执行 |
| 正在提交 | 禁止重复确认，持久保存原体和操作 ID | 单事务、幂等操作绑定、真实回执 |
| 提交超时／响应丢失 | 结果待核实，先查询原操作 | 同键同体可恢复；同键异体拒绝 |
| 已执行但刷新失败 | 保留成功，允许重刷 | 刷新错误不回滚已提交事实，不建议换 ID 重做 |
| 版本或修订冲突 | 刷新并重新核对，不自动替换版本 | 不执行旧草稿，返回明确原因 |
| 引用／草稿过期 | 提示重新选择／生成 | 不因恢复窗口或重放请求延长有效期 |
| 缺少规划／执行接口 | 显示对应模块不可用与原因 | 不返回假空库存、不伪造 0、不给成功回执 |

10 秒是 AI 单次流程预算，不是已经实测的手机端总耗时。Android 当前还会执行多次健康／能力／任务／草稿读取；联合验收需分别记录 AI 和用户端完整耗时，不用模型调用时间替代。

## 13. 建议开发顺序与联合验收

### 13.1 顺序

1. T01：确认最终候选包、HTTPS、登录与家庭选择；已有 ADD/MOVE/CONSUME/手动 PLAN_ADD 做回归基线。
2. T02＋T03：前端补当前任务路由与字段保存；后端完成引用适配器，两侧对齐对象有效期和修订。
3. T04＋T05：前端补动作表单，后端补 OPEN/DISCARD 确认事务、事件与回执；先隔离环境验收。
4. T06：后端提供完整规划快照和事实来源，前端承接消费统计；数据不充分的家庭先正常显示不足。
5. T07：复用相同快照承接条件预测，覆盖数据不足与陈旧核对。
6. T08：先开放有依据的只读建议，再完成自动建议草稿的确认重验与单项加入待购。
7. 最终 APK 联合验收通过后，再走受控发布；源码同步、镜像部署与手机验收分别记录。

### 13.2 必须保留的场景

| 场景 | 通过条件 |
|---|---|
| 移动牛奶→多个候选→选择第二批→改目标位置→确认 | 同一任务续接，草稿目标正确，数量不变，正式回执与库存一致 |
| 待澄清时关闭窗口／重建应用 | 找回原任务、修订、字段与候选；不重复付费理解 |
| 提交前退出、提交响应丢失 | 前者不误执行；后者恢复同 operation_id，不重复变更 |
| 查询唯一对象→“它在什么地方” | 使用受信引用重新读位置；另一成员移动后返回新事实 |
| 多对象、引用过期、切家庭／退出登录 | 要求重选，无跨家庭读取或旧回复污染 |
| 开封及重复开封 | 日期正确、数量不变、无重复事件，拒绝未来日期 |
| 部分／全部丢弃与并发库存变化 | 扣量和终态正确，旧版本不扩大执行，不计消费 |
| 消费＋丢弃＋撤销／纠正 | 统计净额符合事件语义，原事件关联完整 |
| 数据不足／分页未完成／核对陈旧 | 明确原因，不伪造零消费、耗尽日期或补货量 |
| 建议生成后另一成员新增待购 | 确认时重验，防止过量／重复待购 |
| 篡改 action／batch／expected_version／引用来源 | 拒绝，库存、事件和回执均无越权变更 |

权限与事务测试需包含两组受控账号／家庭，以及真实 PostgreSQL 并发；不能只用单进程或 SQLite 测试证明并发安全。正式用户数据不用于构造测试库存。

### 13.3 每项交付时填写
