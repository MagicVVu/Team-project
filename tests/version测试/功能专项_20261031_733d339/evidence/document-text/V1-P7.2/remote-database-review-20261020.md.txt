检查日期：2026-10-20，Asia/Shanghai。数据质量和完整性检查的数据库时间为 **20:14:23**。本文件记录该次读取快照，不是后端新功能交付或迁移完成声明。

## 1. 结论

现有数据库适合继续承载家庭库存、AI 任务与确认执行，不需要替换数据库任务网关。正式库当前正常运行，已升级至 0007；但开封、丢弃和完整规划数据尚未完成数据库层承接。

需要特别修正“只补接口就能开放”的理解：数据库 CHECK 约束当前明确排除 OPEN、DISCARD 及对应事件，开封的无数量事件也不符合现有数量约束。后端需要新增可审阅迁移、同步 ORM 和事务代码，再开放能力。

当前只有 3 条库存，没有 AI 任务、草稿、执行回执和消费事件。可以检查真实库存字段；不能据此证明正式聊天执行闭环已经完成，也没有真实消费历史可支撑耗尽预测。空表只表示当前无记录，不能反推从未调用过或记录为何为空。

## 2. 本次检查方式

- 经既有 SSH 账号进入正式服务器，在 backend 容器内复用现有数据库连接。
- SQL 使用 `REPEATABLE READ READ ONLY` 事务，`transaction_read_only=on`，单条语句截止 5 秒，结束 rollback。
- 读取数据库元信息、表行数、约束、索引、聚合质量和关联检查结果；不导出姓名、电话、邮箱、密码摘要、会话令牌、聊天原文或具体库存名称。
- 只读查看数据库容器端口、持久卷、健康状态和既有备份目录元数据；未读取私有备份正文。
- 未运行模型、创建业务任务、变更库存、执行迁移、重启服务或调整数据库权限。常规数据库访问统计不属于业务写入。

## 7. 与待接入功能直接相关的数据库缺口

### 7.1 开封与丢弃需要新增迁移

现场约束：

```text
draft_operations.ck_operation_action
    ADD / MOVE / PLAN_ADD / CONSUME

business_events.ck_business_event_type
    StockAdded / StockMoved / PlanAdded / Consumed

business_events.ck_business_event_quantity
    StockMoved 的 quantity 必须 NULL；其他现有类型必须有正数量
```

因此仅扩展路由、DTO、动作映射或能力开关，会在写操作／事件时触发数据库约束错误。

后端交付要求：

1. 新增 0007 之后的独立 Alembic revision，不直接编辑已部署 0007 冒充迁移完成，也不手工改生产约束跳过版本记录。
2. 同步 ORM、数据库 action 和 event_type 约束，加入业务约定的 OPEN／DISCARD 和 Opened／Discarded 语义。
3. 明确 Opened 无数量变更事件的存储语义，并相应调整数量 CHECK；不能填写虚假的正数量满足旧约束。
4. 复用当前 opened_at、库存状态及数量列；全部丢弃保留记录并置 0／DISCARDED。当前 inventory_items 已支持这两类字段，不必再新增同义列。
5. 与既有幂等操作、决策、事件、版本和回执在同一事务提交；专项测试通过才开放能力。

### 7.2 事件账本还不满足完整统计契约

当前 business_events 有 occurred_at、operation_id、批次关联、前后 JSON 和正数量，但没有独立 recorded_at、稳定 item_key、related_event_id；类型约束也没有 Reversed／Corrected／Adjusted。

后端需要设计真实映射与必要的持久字段。若以不可变 committed_at 等已有事实映射 recorded_at，应说明定义并验证补录场景，不能用 occurred_at 直接冒充录入时间。撤销／纠正要关联原事件，不能从展示文本猜测或重写历史。

现有一操作一事件的唯一约束可以继续服务当前六类单动作；若将来引入关联纠错，需单独审阅事件关系，不因本轮功能随意移除幂等保护。

### 7.3 耗尽预测缺事实，不只是缺查询路由

当前没有消费事件；数据库也没有专用的稳定商品聚合、逐日登记完整性、实物库存核对时间／来源等字段或表。对相关列名的结构检查未发现明确承接；现有 JSON 容器可保存扩展数据，但本次未验证其中有受约束的完整规划事实，不能据此宣称已实现。

即使现在补出 `/internal/v1/planning/context`，也不能生成真实历史。需要业务明确商品映射、历史覆盖、事件水位、可信库存核对；数据不足时正确返回不足。

当前 AI 条件预测要求连续完整观察日等数据门槛，默认至少 14 天、5 条有效消费且分布在 3 个日期，另检查库存核对和异常事实。后端不能造记录或把安装后的每一天标成完整观察日来绕过门槛。

### 7.4 自动补货还缺偏好、待购版本与重验依据

目前有每批 minimum_quantity 和普通共享采购表，但没有完整规划协议中的商品级偏好版本、coverage_days／lead_days、包装容量、shopping_version 和 event_watermark 等明确承接结构。

不要求每个协议字段都新增一列，但后端必须提供稳定、可验证、能够用于确认重验的业务来源。不能把多批次最低库存直接求和当成商品偏好，也不能仅用当前时间戳假装清单版本。

对自动生成的 PLAN_ADD，确认前必须重新核对库存、消费、偏好和待购；当前只执行手动采购草稿的保护仍需保留，直到完整实现。

### 7.5 对象引用缺受信状态生命周期

ai_tasks 已有原文、request_hash、结果、私有 context、revision 和 expires_at，可继续复用。当前没有明确的对象引用来源／建立时间／截止时间字段或独立适配器实现。

不强制另建引用表；后端可以在独立适配层复用现有任务设施，但要保证来源任务、修订、批次、首次建立时间和 15 分钟有效期可核实且不可变，恢复不续期、同键换来源被拒绝。单靠手机回传历史 facts 不足以建立可信引用。

## 8. 运行权限与备份

### 权限

数据库未发布宿主端口；现有家庭权限在后端业务层执行。本次发现应用使用的数据库角色拥有 superuser、createdb、createrole、bypassrls 权限，public 表没有启用 RLS。

这不意味着现有 HTTP 家庭鉴权已经失效，但应用连接权限明显大于日常业务所需。建议后端／部署将迁移维护角色与运行角色分离，逐项核定必要 DML／序列等权限；是否引入 RLS 另行设计，不是这次功能接入的必要重写。当前只读检查没有修改角色或生产权限。

## 9. 推荐后端推进顺序

1. 保留现有数据库、持久卷、任务网关与确认层，先完成最终 APK 的受控联调。
2. 为 OPEN／DISCARD 新增迁移、同步事务与回执，覆盖重复、超量、终态和并发版本变化。
3. 明确事件与稳定商品映射、录入时间、纠错关联和库存实物核对的持久化方案；同步规划快照 schema。
4. 实现规划只读适配器。先能可信返回消费统计或“数据不足”，随后逐步开放条件预测和补货建议。
5. 实现受信引用适配层，复用原任务持久化和修订机制，接通“它在什么地方”。
6. 完成自动建议确认重验，再开放 automatic_planning_commit；分别记录前端承接、后端部署和联合验收。
7. 将业务数据库最小权限、持续备份和恢复演练列为部署交付项，与功能测试分别验收。

详细前后端任务、接口和场景见 [聊天助手协作交接](chat-assistant-team-handoff-20261020.md)。当前报告新增的重点是数据库约束与事实来源要求；不是要求 AI 绕过后端直接读写数据库。

## 10. 本次结论的边界

本次确认结构、计数、指定质量检查、约束和采样运行状态；未进行全库物理损坏扫描、性能压测、真实用户登录越权测试或灾备恢复演练。维护统计中的 n_live_tup／n_dead_tup 为估计值，不替代实际 COUNT，也不能据其推断业务数据丢失。

所有结论来自只读检查。本地仅记录报告并补充交接链接；没有执行数据库变更或业务写入，没有提交／推送 Git。
