## 2. 常见表达与模型调用边界

零提取位置模板支持下列指代与问法组合，允许边界空白及单个句末标点：

- 指代：它、这一批、这批、这一个、这个、这件。
- 问法：在哪里、在哪儿、在哪、在什么地方、放在哪里、放在哪儿、放在哪、放在什么地方、的位置。
- 验证示例：“它在哪”“它在什么地方？”“这批放在哪里”“这一批放在哪儿？”“这件放在什么地方？”。

有有效受信引用时，按批次 ID 重新读取事实；没有引用时返回 REFERENCE_REQUIRED，不调用模型猜名称。此路径是读取／澄清，不生成写入草稿。

“请告诉我它目前的存放位置”等不在明确模板内的自由表达，仍允许最多一次提取。离线测试验证提取调用次数，不证明真实 DeepSeek 对任意措辞的识别准确率。否定、假设、提示注入和多动作不能因新模板绕过已有输入检查。

## 3. 续接结果成为可校验的调用契约

resolve_reply() 仍为调用方的纯函数，不是新的服务端 HTTP 接口，不读取任务数据库，也不保存最新修订。

输出增加 `protocol_version=p7-reply-routing-1`；保留四种 kind：

| kind | 含义 | 调用方行为 |
|---|---|---|
| clarify | 原任务补字段／选批次 | 使用原 task_id、返回的 revision 与非空 answers 调用已有澄清接口 |
| new_task | 独立新问题 | 保留原文，创建新请求；涉及指代时先由后端核实引用 |
| needs_input | 不能唯一解释／当前答案无效 | 保留输入并询问具体字段或候选，不调用模型猜答案 |
| clear_reference | 用户明确开始新任务 | 清除活动引用，不等于取消或删除历史任务 |

新增互斥校验：只有 clarify 可携带 answers/revision；答案限既有九字段；needs_input 必须有原因且不能静默清引用；clear_reference 必须显式清引用。全部路由判定的 model_calls 恒为 0，new_task 后续理解的调用次数另计。

BoundTask 新增可信 household_timezone，默认上海仅用于兼容及本地测试，正式调用方应从原任务或家庭上下文提供。开封日期辅助校验按该时区判断未来日期，日期原文仍传给 AI；最终日期转换和任务校验以受信上下文为准。

补齐“就第二个吧”等明确序号表达；旧列表序号不可复用到新修订候选。原任务已过期时，“第二个”仍拒绝，但“纸巾在哪里”可进入新任务，不被旧任务阻塞。

## 4. 完整任务验证

测试专用 Workflow 在同一进程内串接 AI 结果、公开任务形状、resolve_reply 和原澄清入口；所有库存都是合成夹具。它没有监听端口、运行用假库存服务、任务数据库或库存写接口。

主要连续场景：

1. 移动牛奶 → 两个候选 → “选择第二批” → 重读 b2 → 生成目标正确、数量不变的待确认草稿。
2. 选批次前数量／位置／版本改变 → VERSION_CONFLICT → 新修订仅剩一个候选 → 旧“第二个”失效 → 用户明确重选 → 草稿使用新事实。
3. 候选删除 → 不生成草稿、不回退第一批；引用对象删除／终态／过期 → 明确要求重选或返回原因。
4. 跨家庭／用户续接 → 不读取目标、不泄露原文、候选或私有上下文。
5. 明确换话题 → 清除活动引用，旧任务保持不变。

专项检查重新读取、目标 ID、预期版本、数量／位置预览、原文、输入凭据、模型调用上限和夹具不被 AI 修改。

## 5. 六类草稿与业务约束

六动作仍为 ADD、CONSUME、OPEN、MOVE、DISCARD、PLAN_ADD；没有新增执行动作或确认 HTTP 端点。

### 已验证的字段语义

- OPEN／MOVE 不包含必填数量；开封数量不变，移动位置改变且数量不变。
- DISCARD partial 采用明确数量与兼容单位；all 从当前批次读取全部量，quantity_source=current_batch。
- 丢弃事件为 Discarded；全量后为 DISCARDED，不混作 Consumed／FINISHED。
- 消耗和丢弃输出库存单位下的精确数量；如 500g 从 2kg 扣减，草稿为 0.5kg、预计剩余1.5kg。
- 目标动作保留真实 batch_id、expected_version 和变更前后事实；缺日期、非法／未来开封日期、超量及单位冲突继续澄清。
- PLAN_ADD 只生成待购草稿，预览 inventory_changes=false，不宣称已采购或写入。

### 本阶段新增的 P7 行为

- ADD 位置缺失／空白或超过100字，先澄清，不输出缺位置的待确认草稿。
- MOVE 目标位置超过100字，先澄清；无效补充仍停在澄清，不截断位置。
- 手动 PLAN_ADD 数量最多三位小数，最大999999999.999，以当前后端 Numeric(12,3)／业务 DTO 为依据；超限要求补充，不舍入。
- 自动规划的数量不符合上述业务限制时，保留已读取事实、目标等计算依据说明，将建议标为 needs_review；清除不可执行的 draft/preview/planning_basis，返回 BUSINESS_PURCHASE_QUANTITY_INVALID。不能删除依据后伪装成可执行的手动计划。

业务准入新增逻辑只在 P7。P0/P1/P2/P3/P5/P6 的旧领域模型和接口没有修改。共享 V1 中文渲染的调整会同时改善 P6/P7 的不足提示，结构化统计字段及计算算法保持不变。

本阶段没有实现草稿确认后的编辑持久化或执行事务；普通草稿编辑、修订保存和重算仍由业务后端负责，不能经澄清修改非缺失字段。

## 6. 统计、预测和补货降级

| 事实不足 | 本地验证结果 |
|---|---|
| 历史未完整取回、缺覆盖日、缺完整性来源 | 显示无法确认完整消费量；不以0小计宣称实际零消费 |
| 有完整窗口但没有有效登记事件 | 明确“未登记到有效消费，不代表实际没有消耗”；不提供耗尽日期 |
| 缺实际库存核对、核对超过168小时或来自未来 | 保留有效消费统计和库存读取事实，移除精确耗尽日期和自动采购草稿 |
| 待购未读完整 | PENDING_INCOMPLETE，不生成采购数量，不把未知待购当零 |
| 缺最低库存及明确采购周期 | EXPLICIT_PURCHASE_PREFERENCES_REQUIRED，不推测用户偏好 |
| 可用库存未核验 | USABLE_STOCK_REQUIRES_REVIEW，要求核对 |
| 规划接口暂不可用 | overview 保留独立读取的库存／风险部分，planning 分区标不可用及原因 |
| 计算采购量超业务精度／范围 | BUSINESS_PURCHASE_QUANTITY_INVALID，不舍入、不生成不可执行草稿 |

充分数据的独立预期：28个完整日登记消费7盒，当前2盒 → 登记日均0.25盒、参考剩余8天；采购覆盖14天＋提前2天 → 目标4盒，抵扣库存2盒与已确认待购1盒 → 建议新增1盒。此为合成事实验证，不是实际家庭的预测结果。

结构化 effective_quantity 为保持原契约仍是数值；status 非 complete 时即使数值为0，也不能在页面脱离状态展示“消费0”。原因可能位于统计 reason_codes、data_gaps 或 sections[].reason_codes，前端分别读取。
