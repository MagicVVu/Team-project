# V1-P8 前后端交接说明

日期：2026-10-23。本地代码已提供，正式 AI 已按用户授权切换为 P8＋DeepSeek；后端和数据库保持原样。前后端仍需合并评审和测试环境联验后各自发布，详见[正式发布记录](正式发布记录.md)。

## 接口契约与 JSON 入口

前后端开发请先查看以下 JSON 契约。它们与本说明一起交接，正文示例不能代替完整的请求、响应、必填字段、枚举和校验约束。

| 调用关系 / 用途 | 契约文件 | 重点查看 |
|---|---|---|
| **业务后端 → AI 服务：本阶段 AI 接入入口** | **[AI OpenAPI：ai-openapi.json](ai-openapi.json)** | `paths` 下的 `POST /agent/message`、`POST /agent/clarification`、`POST /agent/reply-resolution`；以及统计、预测、补货、风险、概览和提交后反馈接口 |
| **Android → 业务后端：本阶段本地候选公开接口入口** | **[后端 OpenAPI：backend-openapi.json](backend-openapi.json)** | 会话消息、`chat-control`、任务/草稿读取、执行预览、确认、取消和操作回执接口；此次未部署后端，不代表其中全部接口已上线 |
| AI → 业务后端：预留的规划读取与内部回执读取接口 | [预留读取 OpenAPI：../V1-P6/backend-read-openapi.json](../V1-P6/backend-read-openapi.json) | `GET /internal/v1/planning/context`、`GET /internal/v1/operations/{operation_id}`；此文件是预留契约，不代表正式后端已实现或可用 |
| 规划读取结果的数据结构 | [规划快照 Schema：../V1-P6/planning-context.schema.json](../V1-P6/planning-context.schema.json) | `PlanningSnapshot` 的作用域、核对时间、完整性标记、事件水位、待购数据及分页字段 |

在 [AI OpenAPI](ai-openapi.json) 的 `components.schemas` 中查看 `ResolveRequest`、`BoundTask`、`ReplyResolution`、`ObjectReference` 和 `ReferenceContext-Input/Output`，核对续接、可信对象引用及有效期结构；在 [后端 OpenAPI](backend-openapi.json) 中查看 `ConversationMessage/Response`、`ControlRequest/Response`、`ExecutionPreview`、`CommitRequest` 和 `OperationReceipt`，核对页面交互与正式执行结果。

前端只调用业务后端公开接口；AI 内部接口由受信业务后端调用。当前消息、澄清和控制字段以本目录的 P8 OpenAPI 为准，旧阶段同名导出保留作历史参考。`ai-openapi.json` 已从正式 P8 AI 服务导出，`backend-openapi.json` 仍对应待发布的本地后端实现；两者仍沿用 AI `0.7.0`、后端 `0.9.0` 的兼容版本号，不能仅凭版本号判断功能是否已上线。

## 二、后端要核对什么

1. 保留旧 `POST /api/v1/agent/messages` 四字段和澄清九字段接口。
2. 部署前确认既有 `conversation-messages` 数据库会话适配、服务令牌、AI `/agent/reply-resolution`、规划读取契约及相关迁移均就绪。AI 请求与响应详见 [ai-openapi.json](ai-openapi.json)；规划读取与快照分别见上表的预留读取 OpenAPI 和规划快照 Schema。
3. 核对执行能力返回包含 `conversation_protocol="backend-conversation-1"` 和 `chat_controls=true`。前端据此选择新协议；动作 flags 继续独立决定可执行性。
4. 受信引用只能由后端依据身份、家庭、源任务/修订、批次和有效期建立。不要直接接受手机提交的历史数量、位置或版本；保持已有可信引用开关及权限校验。
5. 评审本次 `chat_controls.py` 和会话路由。控制接口在认证、家庭权限、任务/草稿修订与有效期校验后，复用 `draft_execution.command/stock_changes/cancel`。未开放动作的编辑仍返回不可执行；取消不要求开放业务执行。
6. 确认提交仍进入既有 `/drafts/{draft_id}/commit`，操作 ID 与请求体稳定绑定，幂等回执原样恢复。草稿控制不代替提交接口。

## 三、前端如何调用

### 1. 发现能力和发送

先 GET `/api/v1/health` 与 `/api/v1/agent/execution-capabilities`。本地增加 15 秒发现缓存，按服务地址和 token 摘要隔离，仅减少重复探测；权限、库存版本和提交检查仍每次由后端执行。

本节公开调用的完整契约见 [backend-openapi.json](backend-openapi.json)，会话请求与响应对应 `ConversationMessage`、`ConversationResponse`。

新会话请求：

```json
{
  "household_id": "22222222-2222-4222-8222-222222222222",
  "text": "两盒，放到冰箱",
  "request_id": "p8-message-unique-id",
  "task_id": "11111111-1111-4111-8111-111111111111",
  "revision": 1
}
```

发送至 `POST /api/v1/agent/conversation-messages`。首次无活动任务时不传 `task_id/revision`；两者必须同时出现。原文、原 request_id 和完整正文发送前落盘，重试不能换 ID 或改正文。每次回复核对协议、请求 ID 和 `inventory_written=false`。

| resolution.kind | 前端行为 | 模型 |
|---|---|---|
| clarify | 更新同一 task，采用服务端新修订；候选顺序对应当前修订 | 零次 |
| new_task | 展示新任务；明确新对象时不继承旧引用 | 首次最多一次；确定性查询可零次 |
| needs_input | 保留当前 task，显示原因，继续补充；帮助/感谢也可用此分支 | 零次 |
| clear_reference | 清除当前对象引用/活动任务，保留历史和回执 | 零次 |

候选按钮和补字段表单在新协议下同样走上述会话入口，避免手机已更新修订而服务端会话还停留旧修订。按服务端返回的字段和候选生成字面补充，不拼接猜测物品名。旧服务才使用原结构化澄清入口。

### 2. 自然修改和取消

有未提交草稿且 `chat_controls=true` 时，先调用：

`POST /api/v1/agent/tasks/{task_id}/chat-control`

```json
{
  "text": "改成三盒",
  "task_revision": 2,
  "draft_revision": 1,
  "edits": {}
}
```

以下是合成新增草稿的响应示例：

```json
{
  "protocol_version": "p8-chat-control-1",
  "kind": "edit",
  "task_id": "11111111-1111-4111-8111-111111111111",
  "draft_id": "44444444-4444-4444-8444-444444444444",
  "task_revision": 2,
  "draft_revision": 1,
  "edits": {"quantity": "3", "unit": "盒"},
  "preview": {
    "command": {
      "action": "ADD", "name": "牛奶", "quantity": "3", "unit": "盒",
      "location": "冰箱", "purchased_at": null, "label_expiry": null
    },
    "before": null,
    "after": null,
    "prospective": true,
    "inventory_written": false
  },
  "reply": "修改内容已校验，请核对更新后的草稿。尚未执行，需要你确认。",
  "inventory_written": false,
  "model_calls": 0
}
```

成功 edit 的 `preview` 为 `{command,before,after,prospective:true,inventory_written:false}`，完整字段详见 [backend-openapi.json](backend-openapi.json) 中的 `ControlRequest`、`ControlResponse` 和 `ControlPreview`。新增/加入采购没有已有库存 before/after，二者为 null；不得据此捏造资源 ID。

| kind | 含义 | 客户端处理 |
|---|---|---|
| edit | 字面字段经正式规则校验后的预览 | 保存返回 edits 和 preview，展示数量/位置/日期摘要；等待明确确认 |
| cancel | 已保存草稿取消决定，库存不变 | 标记已取消，清除当前引用；不显示已执行 |
| needs_input | 混合指令、换目标、无法确定的编辑 | 保留任务和已有字段，要求更具体地说明 |
| not_control | 普通提问或新任务 | 用之前保存的同一个 conversation 请求继续发送 |

仅支持字面数量（含一至十）、位置和开封日期等已有可编辑字段。全部丢弃不允许通过编辑数量变成部分丢弃；动作、批次、家庭、预期版本不接受改写。

“校验草稿”携带当前表单 `edits` 可以重新得到预览。服务端不覆盖原草稿，不提升修订，不写库存；所有编辑均由客户端保存并在确认时显式提交。修改表单后旧预览立即作废。相同任务存在处理中续接时，取消返回 `CONVERSATION_PROCESSING`，先恢复核实，不强行取消。

新增草稿的可空 `purchased_at/label_expiry` 清除时发送 JSON null；回到表单显示为空字符串。开封日期不是可空字段，不使用此规则。被拒绝的文字编辑不会覆盖或隐藏原有可编辑草稿。

### 3. 确认与恢复

确认、执行预览和正式回执的结构详见 [backend-openapi.json](backend-openapi.json) 中的 `CommitRequest`、`ExecutionPreview` 和 `OperationReceipt`；不要将 AI 草稿响应当作业务成功回执。

- 确认前重新核对草稿和执行状态；显示经校验的物品、数量、位置/日期。只有用户点击最终确认后才发送正式 commit。
- 提交前保存 `operation_id`、task/draft 修订及完整 edits。重复恢复只能传原 ID 和完全相同的正文。
- 页面关闭/应用重建后先 GET 原任务/执行状态/回执。没有任务 ID 的原始消息，仅允许原 request_id、原正文恢复；不能静默变成另一种协议。
- `AI_OUTCOME_UNKNOWN` 可能已调用过模型：保存返回 task_id 提示，只 GET 原任务核实，不自动重提取。任务仍 processing 时显示结果待核实。
- `TASK_REVISION_CONFLICT`、`DRAFT_REVISION_CONFLICT` 或库存版本变化：读取当前任务，丢弃被拒绝的临时 edits，要求重新核对；不自动把新版本塞进旧 commit。
- token 变化、退出、切换家庭后不自动续接原请求；原家庭历史请求和回执仍保留用于 GET 核实。
- 已获得正式成功回执后刷新失败，保留“已执行”，仅提示库存/清单刷新失败，不重新提交。
- 保留 `UNKNOWN/PROCESSING/CLARIFICATION/PENDING/SUBMITTING/COMMITTED/CANCELLED/FAILED/CONFLICT/EXPIRED/UNSUPPORTED/ANSWERED` 的独立含义。聊天文字不能驱动成功状态。

## 四、待联合验证清单

| 场景 | 预期 |
|---|---|
| 移动牛奶→多个候选→“第二个就行”→改位置→确认 | 同一任务选择正确批次，最新版本预览，只有正式 commit 产生一次移动 |
| 新增牛奶→“两盒，放到冰箱”→“改成三盒”→确认 | 同一任务补多个字段；编辑只预览；确认后真实新增3盒 |
| 查询唯一对象→“它在什么地方” | 后端核实引用、AI重新读事实，零模型续接 |
| 多对象/过期引用/批次删除/终态/跨家庭 | 要求重选或权限拒绝，不默认选第一批 |
| “你好/谢谢/帮助”后继续原任务 | 不丢字段或已编辑草稿，不刷新引用有效期 |
| 开封/部分及全部丢弃 | 根据能力开放，开封数量不变，丢弃事件与消费分离；全部数量来自当前库存 |
| 补充期间/确认前关闭窗口，提交响应丢失 | 原 task、revision、operation_id 可恢复，不重复提取或执行 |
| 数据不足的统计/预测/补货 | 显示可靠事实、更新时间、缺失资料和不可用原因，不伪造零消费/耗尽日 |
